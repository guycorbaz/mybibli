## 3. What went well

- **The architecture held for 24 stories.** rmcp stayed confined to `src/mcp/` behind thin adapters (enforced by the `no_sql_under_src_mcp` audit); every domain rule landed in `services/`. The 11-22 checkpoint could therefore weigh rmcp in isolation and decide to stay on `=3.8.0` (cost record: +16.1 s, +8.6 % clean build at `-j 2`, +3.05 MiB binary; rmcp's empty answers for undeclared capabilities pinned by an inventory test).
- **Shared building blocks emerged early and were reused.** `RefusalClass` / `Refusal` / `FiledProposal`, `proposal_args.rs`, `cover_staging`, `ProposalSubject`, then the shared acceptance core (`acceptance::accept`, `in_retried_transaction`). Stories 11-13 onward were mostly "add a kind" rather than "add a subsystem".
- **The review loop caught real defects, not style.** Examples: an unbounded omnibus range (11-12, High), a lock-order inversion that could deadlock (11-10), a `%2F` bypass of the hidden-path guard on `/covers` (11-14), concurrent same-name series creations (11-17), a background cover fetch overwriting an accepted cover (11-18). Six stories also found tests that passed vacuously or for the wrong reason (11-3, 11-4, 11-5, 11-6, 11-11, 11-14), which led to mutation-style proofs.
- **The decision log scaled.** 225 D-11-* entries with Context / Chosen / Rejected / Reversible made an unattended epic auditable; superseding entries name what they replace.
- **Security was designed in, not bolted on.** The server never downloads an agent-supplied URL (threat model § 5.9); staged covers are never public; revoking a key stales its pending proposals; proposals routes are Librarian+.
- **Stop clauses worked.** The 11-21 UX-DR32 stop clause fired (the bar already overflowed at `lg`: +4 px fr, +8 px de); the agent stopped and the project lead decided (switch at `xl`; CR #547 sidebar deferred until after epic 11) instead of the agent improvising a layout change.
- **The single-tenant constraints held.** No per-user scoping was introduced; lock order and deadlock-only retries follow the issue #16 doctrine.

## 4. What did not go well / recurring patterns

### 4.1 Local compute and memory
- A session was lost to a kernel OOM at the start of the epic (11-8 resumed from local commits); one full `cargo test` was killed by memory pressure in 11-21; `cargo test` was also stopped by `mem-guard` in 11-2 (twice) and 11-4.
- Outcome: `mem-guard`, `-j 2`, one heavy job at a time, and a shared `CARGO_TARGET_DIR` (one build at a time) became the norm. The project lead set new rules on 2026-10-29 (see § 6).

### 4.2 Agent hand-offs and push cadence
- An agent handed back mid-step (11-16) instead of finishing through the merge; the brief gained "never hand back mid-step".
- Two agents pushed only once (11-18, 11-20) before that became the rule; the others followed the per-step push of Rule #10/#15 and paid one full CI run (~15 min) per push.
- The CI workflow ran twice per push on story branches (push + pull_request). 11-23 (PR #551, D-11-23-5, decided by the project lead) limited `push` to `main`. Side effect recorded in #550: a branch without a PR, a PR in merge conflict, or a PR stacked on another branch gets no CI run.

### 4.3 E2E isolation
- **Order dependency (#528):** `empty-states`, `dewey-code` and `classification-fieldset` assume no series exists; specs creating series only pass because their file names sort later (D-11-11-6). Seven stories had to respect that workaround.
- **Fixed `specIsbn` values** prevent re-running a spec on a non-reset stack (11-1, 11-2, 11-7, 11-17, 11-23): every full run needs `e2e-reset.sh` first.
- **Known flaky test:** `shelving.spec.ts` "second shelve removes the earlier undo button" (#499) — seen in 11-1, 11-4, 11-7, 11-8, 11-19; passes on retry.
- **Main-branch CI went red twice on E2E after merges** (not recorded in the story files): after 11-19 (#543), `metadata-cover-proposal-accept.spec.ts` got a 500 on key revocation (`helpers/api-keys.ts:58`); after the docs chore #549, `highest-label-codes.spec.ts` read V9999 where it expected V9998 (another spec's label in the shared DB). Both passed on the next merge. A third red run (after 11-16) was a Docker Hub registry error. Tracked as action A3 (#554).

### 4.4 Environment gotchas
- CI's MariaDB uses the server default charset: string expressions decoded as VARBINARY in dynamic queries (11-9 CI red; `CAST(… AS CHAR)` became a pitfall carried in every later brief).
- The repo is not fully rustfmt-formatted: `cargo fmt -- <files>` reformatted the whole crate (11-7). Agents format only the leaf files they touch; CI does not run `fmt`.
- Askama escapes `<` / `&` as numeric entities; router tests must assert on them (11-16 onward).

### 4.5 What agents could not do
- The MCP Inspector check was never run by an agent (refused by the session permission policy in 11-6, 11-22 and 11-24). 11-22 reproduced the client handshake in a test; 11-24 wrote the check as an operator procedure in the manual. It must be done by the project lead.
- A comment an agent tried to post on CR #547 was refused by the permission policy; the CR does not carry it.

### 4.6 Product questions left open by design
- #542: accepting any proposal bumps `titles.version`, so every other pending proposal for that title goes stale, whatever its kind. Left for the project lead (D-11-18-11).
- CR #547 (left sidebar instead of the top bar) deferred until after epic 11.

## 5. Error-message review (Foundation Rule #9)

Epic 11 added or changed 249 locale keys per language, 62 of them error-type keys (`error.system.resubmission_delay_invalid`, `admin.api_keys.error_invalid_scope`, `expected_tome.conflict*`, `expected_tome.error.*`, `proposals.error_*`, `proposals.edit_error_*`), all in four locales (only labels such as "ISBN" and "Position" are identical to English, legitimately).

Sampled against `docs/error-message-style.md`:
- **Operation / conflict errors comply** with "what happened → why → what you can do": e.g. `proposals.error_accept_failed`, `proposals.error_cover_missing`, `proposals.error_changed`, `expected_tome.error.version_conflict`, `expected_tome.error.database`. No HTTP codes, SQL or internal names.
- **Field hints are terse** and state the bound (`proposals.edit_error_position_range`, `expected_tome.error.title_too_long`).
- **Outliers (Low):**
  1. `proposals.error_accept_kind` — "Accepting this kind of proposal is not available yet." Since 11-18 every kind can be accepted; the message is now only a defensive branch (`AcceptError::WrongKind`) and "yet" is misleading; no next step.
  2. `expected_tome.conflict` — "…: nothing was attached." states only what happened; it relies on the `conflict_held` / `conflict_elsewhere` / `conflict_out_of_range` line that follows for the why and the next step. Acceptable as a pair; worth a note in the guide.
  3. Capitalisation of the `proposals.edit_error_*` field hints is mixed: some start with a capital ("Series name is required", "Position must be between…"), others are lower-case fragments ("a value is required", "at most %{max} characters"). The lower-case ones are appended after a field label, but the family reads inconsistently.

Recorded as follow-up work (action A6, #555), not fixed in this retrospective (guide: "record outliers rather than fixing silently mid-retro").

## 6. Process changes from the project lead (2026-10-29) and proposed rule amendments

Rules set by the project lead during the epic:
- **One push per story**, after the review loop and the full local gates; intermediate BMAD steps are committed locally only.
- **Targeted gates between iterations** (`cargo check`, clippy, touched test binaries, affected E2E specs); **full gates once**, on the final code, just before the push.
- **Shared `CARGO_TARGET_DIR`**, one build at a time; no release builds unless a measurement needs one.

These contradict the current text of several Foundation Rules. **Proposed amendments — for the project lead to accept or reject; CLAUDE.md is NOT edited by this retrospective:**

- **Rule 10 (Commit & Push Cadence)** — keep "commit after every workflow step", replace the push sentence with: *"Commits stay local until the story is complete. Push ONCE per story, after the code-review loop is clean and the full local gates have passed on the final code (Rule 13). Push again only to fix a CI failure (Rule 18)."*
- **Rule 13 (Local Testing Before Push)** — add a two-tier gate: *"(a) between dev iterations and review rounds run targeted gates only — `cargo check`, `cargo clippy -- -D warnings`, the test binaries the change touches, the affected E2E specs; (b) run the full gates — `mem-guard cargo test -j 2`, `cargo sqlx prepare --check`, `CI=true npx playwright test --workers=2` on a stack freshly reset with `./scripts/e2e-reset.sh` — once, on the final code, just before the single push; re-run them only if code changes afterwards. Heavy commands run under `mem-guard`, one at a time, with the shared `CARGO_TARGET_DIR`."*
- **Rule 15 (Draft PR at Story Start)** — replace with: *"Open the PR (not draft) at the story's single push, titled `Story N-M: …`. Until then the local branch and the story file are the visibility radar."* (Rationale: a draft PR at the first commit requires a push, which the new policy forbids; and since #551 CI runs only through the PR.)
- **Rule 18 (CI Gating)** — add: *"CI runs only on `main` and on pull requests targeting `main` (#551). A branch without a PR, a PR in merge conflict, or a PR based on another branch gets no run — open the PR or resolve the conflict first, or trigger the workflow manually if `workflow_dispatch` is added (#550)."* And: *"Never hand back mid-step: an autonomous agent waits for CI and finishes through the merge."*
