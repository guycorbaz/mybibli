# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Test Commands

```bash
# Build and check
cargo check                          # Fast type-check
cargo build                          # Full debug build
cargo clippy -- -D warnings          # Lint (zero warnings policy)

# Unit tests
cargo test                           # Run all unit tests
cargo test config::                  # Run tests in a specific module
cargo test test_name -- --nocapture  # Run single test with output

# DB-backed integration tests (tests/find_similar.rs uses #[sqlx::test])
docker compose -f tests/docker-compose.rust-test.yml up -d  # Starts dedicated MariaDB on port 3307
SQLX_OFFLINE=true DATABASE_URL='mysql://root:root_test@localhost:3307/mybibli_rust_test' \
    cargo test --test find_similar --test seed_gate   # Each test gets a fresh DB via #[sqlx::test(migrations = "./migrations")]

# E2E tests (requires running app + MariaDB)
cd tests/e2e && npm test             # Run all Playwright E2E tests
cd tests/e2e && npx playwright test specs/journeys/catalog-title.spec.ts  # Single spec

# E2E with Docker (full stack)
cd tests/e2e && docker compose -f docker-compose.test.yml up -d
cd tests/e2e && npm test

# E2E stack reset — single-command teardown + rebuild + wait-for-ready.
# Use when local DB state is polluted and tests expect a fresh baseline
# (see Epic 7 retrospective Action 4 for the backstory).
./scripts/e2e-reset.sh

# Flake gate (run before committing E2E changes) — enforced by CI in the e2e job
grep -rE "waitForTimeout\(" tests/e2e/specs/ tests/e2e/helpers/ && exit 1 || true

# Database
cargo sqlx prepare                   # Regenerate .sqlx/ offline cache after query changes
cargo sqlx prepare --check --workspace -- --all-targets  # Verify cache matches source (pre-commit check)

# i18n — REQUIRED after adding/changing locale keys
touch src/lib.rs && cargo build      # Force i18n proc macro to re-read YAML files

# CSP report-only mode (story 7-4) — observe violations without blocking
CSP_REPORT_ONLY=true cargo run       # Switches header to Content-Security-Policy-Report-Only

# Bypass the first-launch setup wizard (story 8-8) — accept "1" / "true" / "TRUE" only.
# Used by the E2E suite (already set in tests/e2e/docker-compose.test.yml) and any dev
# loop where seed migrations have already created an admin user. `cargo run` against a
# clean DB without this var fires the wizard at /setup.
MYBIBLI_SKIP_SETUP=1 cargo run
```

### Memory guard on the workstation

Prefix every heavy command with `mem-guard` (a station-wide tool in `~/.local/bin`, not in this repo): full `cargo test`, `cargo clippy --all-targets`, the first build of a fresh worktree, `./scripts/e2e-reset.sh`, the Playwright suite. Pass the rule on to every subagent prompt that compiles or tests.

```bash
mem-guard cargo test                 # runs in its own cgroup: 10G + 1G swap cap
mem-guard npx playwright test        # at most 2 guarded jobs station-wide; a third waits
mem-guard --status                   # slots in use, oomd policy, recent OOM kills
```

Why: `systemd-oomd` kills the whole terminal cgroup — the Claude Code session included — when memory pressure on the user slice exceeds 50 % for 20 s. Two sessions died that way on 2026-10-27 (a full `cargo test` in a fresh worktree while another project was building). Under `mem-guard` a peak kills the command (exit 137) and the session survives. Fast, light commands (`cargo check`, a single targeted test, `cargo fmt`) need no guard. Without user systemd (CI), the tool runs the command unguarded.

## Foundation Rules

These apply to ALL sessions without exception.

1. **DRY** — No duplicated code. Shared utilities go in `src/utils.rs`.
2. **Unit Tests** — All code must have unit tests, written alongside implementation. No code ships without corresponding unit tests. Bug fixes must include a regression test.
3. **E2E Tests** — All features and bug fixes must have Playwright E2E tests covering the real user scenario. Must include a smoke test covering the real user journey (no cookie injection shortcuts). A feature without E2E coverage is not done.
4. **Code Language** — All code, comments, variables, and commit messages in English.
5. **Gate Rule** — No milestone transition until ALL tests (unit + E2E) are green.
6. **Code Review Loop** — After code review, if any Medium+ severity findings are discovered, re-run the review after fixes. Story is clean only when a full pass finds no Medium+ issues.
7. **E2E Smoke Test per Epic** — Each epic MUST have at least one E2E test that starts from a blank browser (no injected cookies), performs the epic's core user journey end-to-end (e.g., login → navigate → perform action → verify result). If this test fails, the epic is NOT done.
8. **Retrospectives** — Mandatory at the end of each epic, never postponed. Run the complete test suite before each retrospective.
9. **Error Message Quality** — All user-facing error copy follows [`docs/error-message-style.md`](docs/error-message-style.md): field-validation hints stay terse; operation/conflict/system errors follow "What happened → Why → What you can do" in plain language (no HTTP codes, no jargon, no stack traces). At each epic retrospective, sample the `error.*` keys touched that epic and review them against the guide; messages are iteratively improved via retrospectives from real usage.
10. **Commit & Push Cadence** — Commit after every workflow step (after `create-story`, after `validate`, after `dev-story`, after `code-review`). Push only on demand or at epic close (after retrospective) — this saves CI minutes and keeps the remote history aligned with epic milestones rather than intra-story churn.
11. **Issue Tracking on GitHub** — Change requests, bugs, known-failures, code-review findings, and any other deferred work are tracked as GitHub Issues (labels `type:change-request`, `type:bug`, `type:known-failure`, `type:code-review-finding`). Never re-introduce a local markdown tracking doc (`deferred-work.md`, `known-issues.md`, etc.) — GitHub Issues is the single source of truth.
12. **Source File Size Limit** — No single source file should exceed 2000 lines. When a file approaches this limit, split it into focused modules or separate concerns into `src/services/`, `src/models/`, or new submodules. Maintainability and testability degrade when files grow beyond this threshold.
13. **Local Testing Before Push** — ALWAYS test locally before pushing to GitHub. Minimum: (1) `cargo check` + `cargo clippy`, (2) `cargo test` for affected modules, (3) if story includes E2E or Docker, run `./scripts/e2e-reset.sh` and `docker compose -f tests/e2e/docker-compose.test.yml up` to verify the full stack builds and starts without errors, (4) for any spec change that touches shared-DB state (seeding entities, deleting entities, asserting list emptiness), the truth gate is `CI=true npx playwright test --workers=2`, NOT the default-worker count — local high-parallelism (e.g. 14 workers) exposes scheduling-order races that vanish at CI's 2-worker shape, and trusting the default-worker run there leads to false-green pushes. Do NOT push if local tests fail. This prevents CI failures and wasted build minutes.
14. **One Branch = One Story** — A `story/N-M-slug` branch carries the work of story N-M only. Never pile multiple stories on the same branch. Before starting a new story: (a) working tree clean, (b) on `main`, (c) `git pull --ff-only` to sync with `origin/main`. Refuse to start otherwise. After a story PR merges: delete the local branch immediately (`git branch -d story/N-M-slug`); the remote branch is auto-deleted via the GitHub repo setting `delete-branch-on-merge`.
15. **Draft PR at Story Start** — Open a draft PR (`gh pr create --draft`) at the first commit of every story branch. Effect: `gh pr list` becomes the visibility radar for in-flight work. A story branch with no PR is an anomaly. CI runs continuously on the branch, surfacing regressions early.
16. **Sprint-Status Ownership** — `_bmad-output/implementation-artifacts/sprint-status.yaml` may only be modified in the PR of the story that is transiting status, and only for that story's line (plus the `last_updated` header). Modifying another story's status from a sibling branch is forbidden — it produces the multi-branch drift that destroys the source-of-truth property. Cross-cutting epic-level edits go in their own chore PR.
17. **Epic Close Checklist** — Before marking an epic `done` and running its retrospective: (1) all `story/N-*` branches of the epic are deleted (= all merged into `main`); (2) all stories of the epic are `done` in `sprint-status.yaml` *on `main`* (not just locally on a branch); (3) all open code-review findings are migrated to GitHub Issues per Rule 11; (4) the retrospective is launched immediately, *never* deferred to the next epic (reinforces Rule 8). If any item fails, the epic is not done.
18. **CI Gating Between Push and Next Action** — After every push to a story branch, WAIT for CI to finish before opening another PR, applying more patches, starting a new story, or pushing additional commits to the same branch. Then act on the result: (a) **CI green** → merge the PR (squash via `gh pr merge --squash` for story branches; preserve commits via `gh pr merge --merge` only when explicitly requested); (b) **CI red** → diagnose the root cause from the CI logs (`gh run view --log-failed`), reproduce locally if reasonable, fix, push, and wait again. Repeat until green. Never push speculative fixes without reading the failure first — guessing causes fan-out churn and burns CI minutes. Never bypass CI by force-merging or merging with `--admin` without explicit user authorization. The only legitimate reason to push during a still-running CI is a hotfix to the same failure CI is about to surface (e.g., a typo you noticed seconds after the push).
19. **Release Doc Sync** — When releasing a new version (cutting a tag, bumping `Cargo.toml`, or shipping a release artifact), update EVERY piece of documentation that references a version number, in the same change-set or a same-day follow-up PR. The release is not done until all of these reflect the new version:
    - **User manual** under `docs/manual/{en,fr}/` — chapter 1 "Current version" line, chapter 8 / 12 "What's new" sections, rebuild PDFs and commit them on the release branch so `git checkout vX.Y.Z` shows docs in sync.
    - **README.md** — Status line, Live production install label, install snippets, version-referenced badges/shields.
    - **ROADMAP.md** — "Current stable" header, move the released entry from planned → shipped, add patch entries for `1.X.Y` releases.
    - **`docs/dockerhub-overview.md`** — Tags list (most-recent first), any version mentioned in the install snippet, feature list if changed.
    - **`website/index.html`** — Nav badge, hero "vX.Y.Z is live" headline, feature panels, CTA.
    - **`website/roadmap.html`** — Mirror of ROADMAP.md (Now / Next / Later sections, shipped vs planned).
    - **GitHub Release page** — Created from the tag via `gh release create` with release notes summarizing the bundle; not just a tag.
    - **`_bmad-output/implementation-artifacts/sprint-status.yaml`** — `last_updated` header if it carries version semantics.
    - Any other doc file that mentions the previous version (grep `vX.Y.Z` of the previous version before merging — `grep -r "v1.7.5" docs/ website/ README.md ROADMAP.md` for a v1.7.5→v1.7.6 cut).
    - **Grep ALL stale versions, not just the immediately-previous one** — `grep -rnE "v?1\.[0-9]+\.[0-9]+" website/ docs/ README.md ROADMAP.md` and review every hit that is not a deliberate historical reference (shipped-release sections, What's-new chapters). Lesson from the v1.13.0 cut (2026-07-24): `website/about.html`'s nav badge sat at `v1.7.1` through six releases because each cut only grepped for its own predecessor; `sitemap.xml` `lastmod` had likewise been stale since May. Version-bearing surfaces easy to forget: `website/about.html` badge, `website/sitemap.xml` lastmod, JSON-LD `softwareVersion` blocks in every `website/*.html`.

    A version bump that leaves any of these showing the previous version is a broken release. The recurring failure mode is forgetting `ROADMAP.md` / `dockerhub-overview.md` / `website/` because the release-cut PR focused on the manual + README — those three are the load-bearing follow-up checklist.

## Architecture

**Stack:** Rust 2024 + Axum 0.8 + SQLx 0.8 (MariaDB) + Askama 0.15 + HTMX 2.0 + Tailwind CSS v4

### Deployment model: single-tenant

mybibli is designed and operated as a **single-tenant** application — one library instance per deployment (typical: a household NAS or a small association). The auth surface (CSRF, cookie attributes, session policy) is formalized end-to-end in [`docs/auth-threat-model.md`](docs/auth-threat-model.md) — read it before changing anything in `src/middleware/csrf.rs`, `src/middleware/auth.rs`, the `sessions` schema, or cookie set/read code. Several design choices follow from the single-tenant shape and are intentionally NOT going to be revisited unless a multi-tenant goal is added explicitly:

- **No per-user authorization scope** on admin routes (issue #54). Every Admin can manipulate every other user. The only ownership-style guard is the self-deactivate / last-active-admin pair in `services/users.rs`.
- **MariaDB deadlock retry, not topology fix** (issue #16). `LoanService::register_loan` retries on SQLSTATE 40001 / MySQL 1205 up to `LOAN_CREATE_MAX_ATTEMPTS` times, AND ONLY on those two. `sqlx::Error::PoolTimedOut` and other pool-level / network-level failures are intentionally NOT retried (pool saturation is structural — retrying the same starved-pool burst makes it worse). Sufficient for single-librarian load; would need to be revisited (lock ordering + `READ COMMITTED` + optimistic locking on `volumes.version`) if concurrent librarians become a goal.
- **One settings table for the whole instance**. `AppSettings` is global, not scoped per user.

If/when multi-tenancy is on the roadmap, both #54 and #16 should be re-opened together; they share the same root cause (no tenant boundary in the schema).

### Source Layout

- `src/routes/` — HTTP handlers. Thin: extract params, call service, return response. `admin.rs` ships the `/admin` page shell and its Health and Trash tabs; the other four tabs live in `admin_users.rs`, `admin_reference_data.rs` (+ `admin_labels.rs`), `admin_system.rs` and `admin_api_keys.rs` — six tabs in all, admin-only.
- `src/services/` — Business logic. All domain rules live here, never in handlers. `admin_health.rs` owns Health-tab data builders (entity counts, trash count, MariaDB version cache, disk usage).
- `src/models/` — Database models. SQL queries, row mapping, `DbPool` parameter.
- `src/middleware/` — Axum middleware: `auth.rs` (Session extractor), `htmx.rs` (HxRequest + HtmxResponse), `pending_updates.rs` (OOB metadata delivery), `logging.rs`, `csp.rs` (Content-Security-Policy + hardening headers, story 7-4).
- `src/error/` — `AppError` enum (Internal, NotFound, BadRequest, Conflict, Unauthorized, Database). All errors must use this — no `anyhow` or raw strings.
- `src/mcp/` — MCP server at `/api/mcp` (epic 11): `mod.rs` (guard: propose key + protocol-version header), `transport.rs` (the only file naming `rmcp`), `tool.rs` (`McpTool` trait), `tools/` (one thin adapter per tool over `services/`), `config.rs` (allowed hosts/origins, body cap).
- `src/metadata/` — External metadata providers. `MetadataProvider` async trait + BnF implementation.
- `src/tasks/` — Background tasks (tokio::spawn). `metadata_fetch.rs` for async BnF lookups; `provider_health.rs` for 5-min provider-reachability pings (story 8-1).
- `src/config.rs` — `Config` (env vars) + `AppSettings` (DB settings table, `Arc<RwLock>`).
- `src/lib.rs` — `AppState { pool: DbPool, settings: Arc<RwLock<AppSettings>> }`.

### Key Patterns

- **Error handling:** `AppError` enum with `IntoResponse`. Conflict = 409, Unauthorized = 303 redirect with HX-Redirect.
- **Logging:** `tracing` macros only — no `println!`.
- **i18n:** `rust_i18n::t!("key")` for ALL user-facing text. Keys in **all four** locale files — `locales/{en,fr,de,it}.yml`. `tests/locale_parity.rs` fails the build on any key present in one file and missing from another, so a key added to en/fr alone turns the DB-integration job red; run `cargo test --test locale_parity` after touching a locale. JS strings: read `<html lang>` and use embedded string map. **CRITICAL YAML FORMAT: locale files must NOT have `en:` or `fr:` as top-level wrapper — the filename determines the locale. Keys start at root level (e.g., `nav:` not `en: nav:`). After adding/changing keys, run `touch src/lib.rs` before `cargo build` to force proc macro recompilation.**
- **DB queries:** MUST include `deleted_at IS NULL` in every SELECT/JOIN on entity tables. Every entity table has `deleted_at`, `version`, `created_at`, `updated_at` columns. **MariaDB type gotchas:** (1) `JSON` columns are stored as `BLOB` — use `CAST(col AS CHAR)` to read as String. (2) `BIGINT UNSIGNED NULL` columns — use `CAST(col AS SIGNED)` and read as `Option<i64>`, then convert to `u64`. (3) Never use `CAST(... AS UNSIGNED)` in SELECT — SQLx can't decode `BIGINT UNSIGNED` into Rust integers reliably. (4) `TIMESTAMP` columns in dynamic queries (`sqlx::query()`) — use `CAST(col AS DATETIME) AS col` to read as `NaiveDateTime`. Without CAST, SQLx returns a type mismatch error. This does NOT affect typed macros (`sqlx::query!`) which handle conversion automatically.
- **Optimistic locking:** UPDATE with `WHERE id = ? AND version = ?`, then `check_update_result()` from `services/locking.rs`.
- **Soft delete:** `services/soft_delete.rs` with table whitelist. Never hard-delete.
- **HTMX responses:** `HtmxResponse { main, oob: Vec<OobUpdate> }`. Check `HxRequest(is_htmx)` — return fragment for HTMX, full page for direct navigation.
- **Session:** Cookie named `"session"` (NOT "session_token"). HttpOnly, `SameSite=Lax` (downgraded from Strict in story 7-3 so the language-toggle top-level POST from a same-site link still carries the session; a drift-compatible risk accepted in the story). Authenticated cookies: no max-age (session cookie). Anonymous-session cookies (story 8-2): `Max-Age=7d` aligned with the daily purge window. Session extractor in `middleware/auth.rs`. Roles: Anonymous < Librarian < Admin.
- **Templates:** Askama templates extend `layouts/base.html` via `{% block content %}`. Nav bar in `components/nav_bar.html`. All page templates must pass `lang`, `role`, `current_page`, `skip_label`, nav labels. **Reusable fragment binding (story 9-19):** when a fragment needs the SAME shape of input on multiple call sites with DIFFERENT named fields, use `{% let alias = self.<surface>_help %}{% include "components/<fragment>.html" %}` in the caller. The fragment reads `{{ alias.* }}`. Concrete example: `templates/components/tooltip.html` is included this way from 11 surfaces; net template footprint ~30 LOC vs ~54 inline. Askama 0.15+ supports `{% let %}` natively.
- **HTML escaping:** Use `crate::utils::html_escape()` — DO NOT duplicate.
- **Pool access:** `pool: &DbPool` from `AppState`. For spawned tasks: `pool.clone()` (Arc internally).
- **SQLx offline:** Run `cargo sqlx prepare` after any query change, commit `.sqlx/`.
- **CSP & hardening headers (story 7-4):** `src/middleware/csp.rs` is wrapped outermost in `routes::build_router` (per AR16: `Logging → Auth → [Handler] → PendingUpdates → CSP`). Strict directive — `script-src 'self'`, `style-src 'self'`, no `unsafe-inline` / no `unsafe-eval`. **Zero inline `<script>`, `<style>`, `style="..."`, `onclick=` etc.** in templates AND in HTML produced from Rust (`feedback_html`, `pending_updates`, `locations` tree, …). All dismiss buttons use `data-action="dismiss-feedback"` (delegated handler in `static/js/mybibli.js`). HTMX trigger filters that need JS evaluation (e.g. `hx-trigger="keydown[key=='Enter']"`) are forbidden — emit a `CustomEvent` from a JS module instead. The `src/templates_audit.rs` `#[test]` walks `templates/` and panics on regressions; pair it with manual greps over `src/` for HTML strings when adding new server-rendered fragments. Toggle observe-only mode with `CSP_REPORT_ONLY=true`.
- **Modal scanner-guard invariant (story 7-5):** `static/js/scanner-guard.js` watches `dialog[open]` and `[aria-modal="true"]` surfaces via MutationObserver. While any modal is open it captures `keydown` at the document-capture phase and either forwards printable chars / Enter to the modal's focused text input or blocks them — preventing a USB scanner burst from leaking into `#scan-field` (duplicate scan) or activating a modal's default-focused Cancel/Confirm button. New destructive action UX MUST use the UX-DR8 Modal component (Epic 9) so it automatically inherits this protection. New `hx-confirm=` attributes are BLOCKED by `src/templates_audit.rs::hx_confirm_matches_allowlist`; the allowlist is empty post Epic 9 — any new `hx-confirm=` is BLOCKED outright by the audit.
- **CSRF synchronizer token (story 8-2):** Every session row carries a `sessions.csrf_token` (VARCHAR(64)) minted on login or on an anonymous visitor's first hit (via `src/middleware/auth.rs::session_resolve_middleware`). Pages emit `<meta name="csrf-token" content="{{ csrf_token|e }}">` in `layouts/base.html`, and every `<form method="POST">` includes a hidden `<input name="_csrf_token" value="{{ csrf_token|e }}">` as its first child. HTMX requests inherit the token via `static/js/csrf.js`'s `htmx:configRequest` listener (sets `X-CSRF-Token` from the meta tag). The `src/middleware/csrf.rs` layer runs on state-changing methods (POST/PUT/PATCH/DELETE), does constant-time compare via the `subtle` crate, and on mismatch emits 403 + `HX-Trigger: csrf-rejected` + `HX-Retarget: #feedback-list` + `HX-Reswap: beforeend` + `Cache-Control: no-store`. `csrf.js`'s `htmx:beforeSwap` listener flips `shouldSwap = true` on that rejection so the server-rendered "Session expired" FeedbackEntry actually lands in the DOM. Exempt-route allowlist is frozen at exactly `[("POST", "/login")]`, policed by `src/templates_audit.rs::csrf_exempt_routes_frozen`. Form coverage is policed by `forms_include_csrf_token` in the same file. **`HX-Trigger` → JS-listener idiom is a NEW project-wide pattern for server-driven UI coordination** — reuse it for future optimistic-locking conflicts, session expiry, etc. Anonymous visitors accumulate session rows; `src/tasks/anonymous_session_purge.rs` deletes them after 7 days of inactivity (authenticated rows are untouched — they're handled by story 7-2's inactivity timeout). `GET /logout` is now `405` — logout flows through a POST form in `nav_bar.html`.
- **Admin page tab pattern (story 8-1):** `/admin?tab=<name>` for deep-linking and history; `/admin/<name>` for HTMX panel swap via `hx-get` + `hx-push-url`. Tab resolution is server-side; invalid `?tab=` falls back to `health`. Every Epic-8 story fills in exactly one panel stub — extend `AdminTab` enum + replace the corresponding `admin_<name>_panel.html` fragment. All admin handlers start with `session.require_role_with_return(Role::Admin, "/admin...")?` so Anonymous bounces to `/login?next=%2Fadmin` and Librarian gets a 403 FeedbackEntry body.
- **User deactivation semantics (story 8-3):** User deactivation uses `users.deleted_at` (soft-delete) — set to `NOW()` on deactivate, `NULL` on reactivate. Deactivation is ATOMIC: a single DB transaction (a) locks the target user row, (b) checks guards (self-deactivate, last-active-admin), (c) updates `users.deleted_at`, (d) deletes all `sessions` rows for that user (`deleted_at = NOW()`), (e) commits. This ensures the deactivated user is immediately logged out and cannot log back in. The `active` boolean is vestigial (schema default `TRUE`) and is NOT toggled by this story. Login predicate requires both `active = TRUE AND deleted_at IS NULL`.
- **Reference data CRUD pattern (story 8-4):** Four taxonomy tables — `genres`, `volume_states`, `contributor_roles`, `location_node_types` — share one CRUD shape (`list_all`, `find_by_id`, `create`, `rename`, `soft_delete`, `count_usage`) on their respective models. Deletion is gated by a **usage-count guard** (`SELECT COUNT(*) WHERE <fk_col> = ? AND deleted_at IS NULL`), NOT by `services::soft_delete::ALLOWED_TABLES` — the four reference tables are deliberately NOT in that whitelist (Trash view doesn't list ref entries; soft-deleted ref entries are recovered by re-creating with the same name, which transparently reactivates the row). `LocationNodeTypeModel::rename` is **transactional and cascades** the new name into every matching `storage_locations.node_type` row because that FK is a `VARCHAR(50)`, not an integer — intentional asymmetry (rename cascades by name; delete refuses if any references). Soft-delete name reuse hits a UNIQUE collision; the model layer transparently reactivates the soft-deleted row and returns `CreateOutcome::Reactivated(id)` so the handler picks the "Reactivated" feedback copy. All 19 admin handlers live in `src/routes/admin_reference_data.rs` (Foundation Rule #12 — kept admin.rs under 2000 lines). Destructive actions use the InlineForm Modal pattern (`templates/fragments/admin_ref_delete_modal.html`, `admin_ref_loanable_warning_modal.html`); `hx-confirm=` allowlist stays frozen at 5. Admin modals mount into the stable `<div id="admin-modal-slot">` slot in `layouts/base.html` (decoupled from panel lifecycle). Reference-data values are NEVER translated (NFR41) — only UI labels are localized. Inline-edit affordance via `static/js/inline-form.js` (delegated `data-action` handlers, CSP-clean).
- **System settings pattern (story 8-5):** The `settings` table is K/V (one row per setting, each with its own `version INT` for partitioned optimistic locking — concurrent edits to *different* settings never collide). `AppSettings` (`src/config.rs`) is the in-memory cache wrapped in `Arc<RwLock<>>`; `AppSettings::load_from_db` re-validates every row on each load (clamping, fallback-on-invalid, log warns). Admin saves go through `src/routes/admin_system.rs` — three forms (Loans / Metadata Providers / Language) each posting to its own endpoint and reloading the cache via `load_from_db` + write-lock-swap (no `.await` held while the lock is taken). Read pattern: clone scalar out of the read guard before any `.await`; helpers `state.session_timeout_secs()`, `state.default_language()`, `state.google_books_api_key()` etc. encapsulate this. **Keyed metadata providers read their key per-fetch** from `Arc<RwLock<AppSettings>>` rather than a constructor snapshot, so admin key changes take effect on the very next request — no restart, no provider re-instantiation. OMDb and TMDb are now registered unconditionally; the "no key, skip me" check moved into the providers' fetch methods. **Env-var migration is one-shot** (`config::migrate_legacy_env_vars`) — called from `main.rs` after migrations and before the first `load_from_db`. NOT inlined into `load_from_db` so admin "Clear" actions stay durable for the process lifetime; re-migrates on next boot if the env var is still set in `docker-compose.yml`.
- **First-launch setup wizard (story 8-8):** `src/middleware/setup_gate.rs` redirects every non-whitelisted request to `/setup` while the wizard is active. The active predicate is `(active_admin_count == 0) AND (settings.setup_completed_at IS NONE)` — both halves must hold. Cached in `AppState.setup_gate: Arc<RwLock<SetupGateState>>` so reads are lock-only (no DB round-trip per request). Step 1 (admin row inserted) and Step 4 (`setup_completed_at` written) call `middleware::setup_gate::refresh` to recompute the predicate. Whitelist passes through `/static/*`, `/covers/*`, `/health`, and `/setup*`. Layer order at request time: `CSP → SetupGate → SessionResolve → Locale → CSRF → handler`. The wizard is single-use: once `setup_completed_at` is set, `/setup` returns 404 and the gate is a no-op forever. - **Scan-undo pattern (polish-2 / #9):** The `/catalog` scan flow lets a Librarian undo the **last** scan action — shelving a volume, or activating a batch storage-location — within a **server-authoritative 30-second window**. The action is logged in the `sessions.data` JSON blob under `last_undoable_action` via `SessionModel::{set,get,clear}_last_undoable_action` (same mechanism as `active_location_id` / `last_volume_label` — **no schema migration**). Type + pure window check live in `src/services/scan_undo.rs` (`UndoableAction`, `UndoKind`, `undo_is_within_window`, `pub const SCAN_UNDO_WINDOW_SECS: i64 = 30` — v1 freeze, mirrors `RECENT_ACTIVITY_DAYS`; a unit test locks it). **Single-action semantics:** each forward action OVERWRITES the log, so only the most recent is undoable. The four `handle_scan` sites (`catalog.rs` shelve at :516/:668/L-code-assign, activate at the L-code branch) capture prior state (a volume's previous `location_id`, or the previous active location + `last_volume_label`) **before** the mutation and record it best-effort (a failed record only degrades to "no undo available" — it never rolls back the scan). The undo affordance is rendered by `crate::utils::feedback_html_undoable` (a `data-action="undo-scan"` button with `hx-post="/catalog/undo"`, CSRF auto-injected by `csrf.js`, CSP-clean, no `hx-confirm`); `static/js/mybibli.js::initScanUndo` disables it on click and removes it after 30 s (UX only — server is authoritative). Undo reverses **location state only** — it never deletes a created title/volume. Tests: `services::scan_undo` unit + `tests/scan_undo_integration.rs` (session-store round-trip, detach / restore-prior / deleted-prior guard, empty + expired paths) + `tests/e2e/specs/journeys/shelving.spec.ts` undo journeys.
- **Auto-purge pattern (story 8-7):** Soft-deleted items are hard-purged after 30 days via two mechanisms: (1) **startup purge** (blocking, bounded by count) runs in `main()` after migrations and before binding the HTTP listener — controllable via `MYBIBLI_SKIP_STARTUP_PURGE=1` for fast-iteration dev/test loops, (2) **scheduled purge** via `src/tasks/auto_purge_scheduler.rs` runs on a configurable cadence (`AppSettings::auto_purge_interval_seconds`, default 86400 = 24h) with `MissedTickBehavior::Skip` so a clock jump doesn't trigger a burst, first run 1 minute after startup. Both use FK dependency ordering via a whitelist (`src/services/soft_delete.rs::ALLOWED_TABLES`) to delete children before parents (e.g., `title_contributors` before `titles`), scoped in transactions per entity family to prevent orphans, with a per-table drain loop (LIMIT 10000 per batch, hard-cap 100 iterations) so back-pressure on a single huge family doesn't leave stale rows. On error (FK violation, DB lock), the family transaction rolls back and logs the error; the daily task continues to the next family (will retry on next scheduled run). Both startup and scheduler runs write a single `admin_audit` row with per-table counts for forensics. Admins can also force permanent deletion from the Trash panel with explicit confirmation (modal friction: type item name to enable button); hard-deletes record an audit entry in `admin_audit` (who, what entity, when). **Self-deletion + last-active-admin guards apply ONLY to the admin manual delete handler (`POST /admin/trash/{table}/{id}/permanent-delete`); the auto-purge scheduler/startup task has no such guard and will hard-delete any row whose `deleted_at < NOW() - 30 DAY`, regardless of role.**
- **Modal lifecycle hardening (polish-1):** Two parallel modal surfaces — **Pattern A** in `#modal-slot` (Return / Delete-volume / Trash permanent-delete; driven by `static/js/modal.js`) and **Pattern B** in `#admin-modal-slot` (ref-data delete / loanable-warning; driven by `static/js/inline-form.js`). Both slots live in `layouts/base.html` outside any HTMX-swappable region so panel re-renders never detach an open dialog. **`HX-Trigger: modal-close`** is the canonical server→client close signal — emit it from any handler that closes a Pattern A or Pattern B modal on success via `HtmxResponse::into_response_with_hx_trigger("modal-close")` in `src/middleware/htmx.rs`. Both modal.js and inline-form.js listen on `document.body` ("Variant A" of the HX-Trigger idiom — post-swap `addEventListener` for events HTMX dispatches natively). This is intentionally distinct from **Variant B** used by CSRF rejection (`HX-Trigger: csrf-rejected`), where `static/js/csrf.js` parses the header in `htmx:beforeSwap` to flip `shouldSwap = true` BEFORE the swap runs — necessary because the rejection response also carries `HX-Retarget` that HTMX would otherwise honor instead. **`X-Modal-Confirm: true` request header** is tagged onto every Confirm-button submit by modal.js's `htmx:configRequest` listener (`originatesFromConfirm()` helper); the `ModalConfirmRetargetGuard` middleware (`src/middleware/modal_confirm_retarget_guard.rs`, wrapped at `src/routes/mod.rs:423` so the request-time layer chain is `Locale → ModalConfirmRetargetGuard → CSRF → handler` — guard sits OUTSIDE CSRF so it sees CSRF-rejection responses and whitelist-preserves their retarget) strips `HX-Retarget`/`HX-Reswap` from error responses so the error body lands in the modal's `<div data-modal-error role="alert">` region instead of being retargeted behind the backdrop. The csrf-rejected case is explicitly **whitelisted out** of the stripping — that retarget must survive. **`AppError::IntoResponse`** has a uniformized contract: every variant (NotFound / BadRequest / Internal / Database / Forbidden) wraps the message in `feedback_html_pub()` and emits `HX-Retarget: #feedback-list` + `HX-Reswap: beforeend`, so an error response from inside a modal Confirm consistently lands in the FeedbackEntry list (via the retarget guard's strip-then-restore-by-default behavior). **New handlers no longer need to manually wrap errors in `feedback_html_pub()` — propagating any `AppError` via `?` is enough.** The **UX-DR8 macro** in `templates/components/modal.html` exposes an optional `inner_form_html` parameter for fragments that need an in-form input region (e.g., the trash modal's type-to-confirm input); CSP-clean — caller `html_escape`s any user data before interpolating. **`showModal()` promotion** runs in `modal.js::open()` and `inline-form.js`'s symmetric observer — declarative `<dialog open>` alone doesn't grant native modal semantics (no `:modal` pseudo, no `::backdrop`, no native Escape, no top-layer). Promotion uses `removeAttribute("open") → showModal()` (NOT `close() + showModal()` — `close()` dispatches a synchronous `close` event mid-tick that races with subsequent listener registration). Modal swap target is `hx-target="#modal-slot" hx-swap="innerHTML"` (NOT `body` + `beforeend`) — guarantees a rapid double-click on the trigger replaces rather than stacks the dialog (#67). The **`hx-confirm=` allowlist** in `src/templates_audit.rs::hx_confirm_matches_allowlist` is frozen empty post-Epic-9 — any new `hx-confirm=` is BLOCKED outright by the audit; every new destructive action MUST use the UX-DR8 macro. New unit + E2E coverage in `tests/admin_trash_modal_lifecycle.rs`, `tests/admin_refdata_hx_trigger.rs`, `tests/e2e/specs/journeys/admin-modal-lifecycle.spec.ts`.

- **MCP layer (epic 11, `src/mcp/`):** `rmcp` is pinned `=3.8.0` (`default-features = false`, `server` + `transport-streamable-http-server`) and named **only** in `src/mcp/transport.rs` (unit test `rmcp_is_confined_to_the_transport_file`); tools implement the mybibli-owned `mcp::tool::McpTool` (serde_json in/out, no `#[tool]` macros) and are registered in `src/mcp/tools/mod.rs` — they are thin adapters over `services/`, **no SQL under `src/mcp/`** (`no_sql_under_src_mcp`). Request order: CSRF `/api/*` short-circuit → 30 s timeout → `mcp_guard` (`ApiKeyPropose`: 401 / 403 `insufficient_scope`; `MCP-Protocol-Version` must be `2025-11-25` or `2026-07-28`, else 400) → rmcp (`Host` / `Origin` allowlists from `MYBIBLI_MCP_ALLOWED_HOSTS` / `MYBIBLI_MCP_ALLOWED_ORIGINS`, 403; body cap ≈ 3.7 MiB, 413) → tool; a non-`initialize` request without the header is refused in the handlers (-32022). Stateless, JSON responses, no CORS, no anonymous `sessions` row. Agent-facing messages stay **English**; web copy is localized. The `initialize` instructions are built per request by `src/mcp/instructions.rs` (story 12-3) from the live registry (`ProviderRegistry::active_chain_names`, `MetadataProvider::is_active`) and `services::cover::COVER_FALLBACK_SOURCES` — a new provider shows there by itself; keep its wording a priority hint, never an exclusion. The registry test requires closed schemas at every level, read tools `read_only`, propose tools not, and propose-tool descriptions containing "does not change the catalog" and "`sources`". A new tool is added to `registry()` in `src/mcp/tools/mod.rs` (a propose tool also to `PROPOSE_TOOLS`), `tests/common/mcp.rs` and `MCP_TOOLS` in `tests/e2e/helpers/mcp.ts`; proposal errors implement `services::proposals::Refusal` (a `RefusalClass`) and are mapped to `ToolError` (`InvalidArguments` / `NotFound` / `Refused` / `Internal`) by `src/mcp/tools/proposal_args.rs`. Threat model: `docs/auth-threat-model.md` § 5.8–5.10.
- **Proposal lifecycle (epic 11):** an agent never writes the catalog (NFR44) — it files a proposal (`proposals` + `proposal_items`, one item per "line", shapes documented in the module docs of `services/series_proposals.rs`, `metadata_proposals.rs`, `cover_proposals.rs`). Filing goes through `ProposalService::file_in` inside the tool's own transaction (lock the filing key row first, duplicate reads non-locking), then `proposals::log_filed` after the commit; each item records its target's `version` (optionally pinned by the agent) and the item's `current` values. Statuses `pending → accepted | rejected | stale`; `stale` sets `decided_at`, never `decided_by` (`decided_by_name` keeps the username). **Acceptance** (`services/acceptance.rs::accept`, one route `POST /proposals/{id}/accept`, kinds in `series_acceptance.rs` / `metadata_acceptance.rs` / `cover_acceptance.rs`): lock proposal → items → targets, `check_staleness_in` (deleted targets; versions for series kinds only) **and** re-check the live catalog state (#521: `title_series`, tome and cover writes bump no version), re-parse and re-validate the stored lines (malformed → 400, still pending), then `transition_in` and apply; stale is a committed decision (200 + warning), a failed apply rolls back (409, still pending); retry only on deadlock (40001), never on lock-wait timeouts. **Lock scope (epic 12 retro A1, adopted 2026-11-01):** a locking read or a multi-table write on `proposals` / `proposal_items` must start from the target index (`FORCE INDEX (idx_proposal_items_target)` + `STRAIGHT_JOIN`) or a PK list — never from a status range: `UPDATE … JOIN proposals … WHERE status = 'pending'` share-locked every pending proposal and deadlocked with a rejection on another title (#571). Each new one ships with a lock-scope regression test like `an_acceptance_on_one_title_does_not_lock_proposals_of_another`. Accepted fields are added to `manually_edited_fields` so re-downloads never overwrite them; staleness is **per field** for metadata and cover proposals (story 12-2, #542, decided 2026-10-30): `services::proposals::version_counts` keeps the `version` comparison for series kinds only, so accepting a cover no longer outdates a metadata proposal on the same title — what makes them stale is a touched field / the cover having changed (`FieldChanged`, `RoleGone`, `CoverChanged`) or a deleted title, plus `proposals::title_moved` (an `identity` snapshot — name, ISBN, media type — in every metadata/cover item; `version` still decides for `current_truncated` and pre-12-2 items); a title correction accepted through a proposal (story 12-5, `title` proposable) carries the new title into the other pending items' `identity` (`ProposalModel::carry_identity_title`), a hand edit does not; every cover write stores a cache-busted URL, and a cover accepted since filing (installed after its commit) also outdates. Equivalence (#535, same story): a rejected metadata proposal blocks **each of its fields** (`newest_overlapping_rejection`, prefix query on `metadata:titles/{id}:`), a rejected cover blocks only **the same image** (`cover:titles/{id}:{sha256}`, `cover_proposals::cover_fingerprint`; legacy keys without fingerprint block nothing new). **Edits** (`services/proposal_edit.rs`, 11-19): a line is edited in place with the agent's values copied to `original_values` (+ `edited_by_name`, `edited_at`); a removed line is a soft-deleted item; the series line, the cover line and the last metadata line cannot be removed; edits pass the filing rules. **History / resubmission:** `proposals.equivalence_key` (kind + target; metadata = title + field set, cover = title + image SHA-256) is computed at filing and recomputed from the live lines at rejection; a rejection blocks equivalent filings (metadata: any shared field) **library-wide** for `proposal_resubmission_delay_days` (settings row, default 90, 0..=3650, Admin → System; new System settings must be whitelisted in `routes/admin_system.rs::fetch_setting_rows`). Revoking a key (`cover_proposals::revoke_key`) marks all its pending proposals stale and discards their staged covers. Web UI: `src/routes/proposals.rs` (labels via its `ProposalLabels::t`), `routes/proposal_edit.rs`, `services/proposal_review.rs`; a Pattern A modal whose response also OOB-updates `#feedback-list` closes with `HtmxResponse::into_response_with_hx_trigger_after_swap("modal-close")`. The nav badge / dashboard pill count every live pending proposal (`Session.pending_proposals`, computed once per Librarian+ page request).
- **Expected tomes (epic 11, `services/expected_tomes.rs`):** a tome of a series the library does not own yet (position, title, optional ISBN; `expected_tomes` table, FK CASCADE to the series, SET NULL to the settling title). A tome is **settled** when its `settled_title_id` is live **and** that title holds the tome's position; otherwise it reads as a gap again. Lock order everywhere: series rows (by id) → tome rows. Settling **attaches** a title (writes `title_series`) only on catalogue events — `/catalog/scan` ISBN arm, manual title creation (`routes/catalog_isbn_banners::isbn_banners`) — and when a tome is created or its ISBN changed; hand assignments, title ISBN edits and tome edits that keep the ISBN only **record** a settlement the series already shows. Settle failures are logged, never fail a scan. The series page renders unsettled tomes in their gap (`place_on_grid`, pure) and lists those that fit no gap under "Expected tomes to review" (#524 states rendered, not prevented). Web errors via `ExpectedTomeError::localized(loc)` / `into_app_error(loc)`; the MCP `Display` stays English. "Add to wish list" dedups on ISBN (or title + note without ISBN).
- **Cover staging and purge (11-14):** proposed covers are decoded, checked (≤ 2 MiB, declared type = magic bytes, #479 limits) and **re-encoded** (≤ 400 px, JPEG 80) before being written to `<COVERS_DIR>/.staging` under a random `<32 hex>.jpg` name (`.tmp-` then rename) — on the covers volume every install already persists. `/covers` answers 404 for any dot-segment (raw or `%2e`, `cover_staging::is_hidden_path`), so staged files are never public; librarians see them through `GET /proposals/{id}/cover` while pending. `cover_staging::{promote, discard, discard_all, is_staged_name}`; `StagingError::Missing` when the file is gone. The server never fetches an agent-supplied URL (SSRF policy, threat model § 5.9). Cleanup: reject → `discard` after the commit; accept → `promote` after the commit (mark `cover_image_url` hand-edited in the decision transaction; the background fetch stores its cover under the title lock and skips a marked cover); key revocation → `discard_all`; and every auto-purge tick (story 8-7 scheduler) runs `cover_staging::purge`, which keeps files of live pending proposals and of proposals accepted less than `PURGE_GRACE` (1 h) ago, and deletes unreferenced files once older than the grace. At most two image encodes run at once; a key holds at most 100 pending cover proposals.

### E2E Test Patterns

Playwright E2E suite lives in `tests/e2e/`. Implementation details below are load-bearing — violating them causes the cascading flake failures documented in story 5-1 (2026-04-05).

**Execution mode:** `fullyParallel: true` (parallel, default workers). Each spec uses unique ISBNs via `specIsbn()` from `tests/e2e/helpers/isbn.ts` and unique V-codes/L-codes/borrower names to ensure no data collisions between specs. All non-smoke specs use `loginAs()` for per-test session isolation.

**Login strategy:**

> **HARD RULE — Foundation Rule #7 (Smoke tests):**
> - ✅ Smoke tests (one per epic) MUST use `loginAs(page)` from `tests/e2e/helpers/auth.ts` — real browser login starting from a blank context
> - ✅ All non-smoke tests also use `loginAs(page)` in `beforeEach` — each test gets its own server-side session for parallel safety
> - ❌ Do NOT inject `DEV_SESSION_COOKIE` — it causes session state pollution in parallel mode
> - Signature: `loginAs(page, role?)` with `role: "admin" | "librarian"` (default `"admin"`). Passwords resolve from `TEST_ADMIN_PASSWORD` / `TEST_LIBRARIAN_PASSWORD` (defaults `admin` / `librarian`), matching seeds in `migrations/20260331000004_fix_dev_user_hash.sql` and `migrations/20260414000001_seed_librarian_user.sql`. The role argument is a typed union so typos fail `tsc --noEmit` — the typecheck is wired into the `e2e` CI job.
> - Env-var overrides apply when Playwright runs on the host (the `_gates.yml` default: only the app runs in docker, `npm test` runs directly). If Playwright is ever moved into docker-compose, pass those vars through the Playwright service's `environment:` block.
> - **`TEST_*_PASSWORD` overrides are local-only.** CI does not set `TEST_ADMIN_PASSWORD` / `TEST_LIBRARIAN_PASSWORD`, so CI always uses the seed defaults (`admin` / `librarian`). If you rotate a seed password in a migration, update the seed itself — do NOT rely on env overrides as the source of truth in CI.

**HTMX wait strategies:** Never use arbitrary `waitForTimeout(N)`. This is enforced by a CI grep gate in the `e2e` job — new `waitForTimeout` calls fail the PR. Use the DOM-state assertions below instead:
```ts
// For V-code creation feedback — wait for the specific V-code text to avoid stale entries
await expect(page.locator(".feedback-entry").first()).toContainText(/V0060/i, { timeout: 10000 });
```
For OOB swaps (e.g., context-banner, pending-updates), wait for the specific swap target to update before asserting.

**Selector policy:** Prefer stable selectors in this priority order:
1. `page.getByRole(...)` — semantic, accessibility-aware
2. `page.locator("#id")` — stable id attributes from templates
3. `page.getByText(/Active loans|Prêts actifs/i)` — i18n-aware regex for user-visible text
4. CSS/XPath selectors — last resort; fragile to Tailwind class changes

**i18n-aware matchers:** All user-visible text in templates goes through `t!()`. Tests must match both EN and FR variants:
```ts
await expect(page.locator("h1")).toContainText(/Active loans|Prêts actifs/i);
```

**Data isolation:** Each spec file generates unique ISBNs via `specIsbn(specId, seq)` from `tests/e2e/helpers/isbn.ts`. The 2-character `specId` is unique per spec file (e.g., `"CT"` for catalog-title, `"LN"` for loans). The mock metadata server (`tests/e2e/mock-metadata-server/server.py`) has a catch-all that returns synthetic metadata for any unknown ISBN, so generated ISBNs always resolve. V-codes must also be unique across specs (no shared V0042, V0071, etc.). Only `provider-chain.spec.ts` uses the real known ISBNs (`9782070360246`, `9780134685991`) because it tests provider-specific metadata content.

**Helper files:**
- `tests/e2e/helpers/auth.ts` — `loginAs()` (real browser login), `logout()` (clears cookies)
- `tests/e2e/helpers/isbn.ts` — `specIsbn(specId, seq)` generates unique valid EAN-13 ISBNs per spec
- `tests/e2e/helpers/accessibility.ts` — axe-core a11y assertions
- `tests/e2e/helpers/loans.ts` — `scanTitleAndVolume`, `createBorrower`, `createLoan`, `returnLoanFromLoansPage`. Canonical loan-flow helpers. `createLoan` submits via direct `page.request.post('/loans', ...)` instead of the HTMX form — the HTMX path proved racy under parallel load (story 5-1c) because `waitForURL(/\/loans/)` was a no-op when the form lives on /loans.
- `tests/e2e/helpers/scanner.ts` — `simulateScan` (scanner burst, 20 ms inter-key) and `simulateTyping` (human pace, 100 ms inter-key). Uses Playwright's native `{ delay }` option — do NOT re-roll `waitForTimeout` sequences.

**Session cookie format:** The `DEV_SESSION_COOKIE` value `"ZGV2ZGV2ZGV2ZGV2ZGV2ZGV2ZGV2ZGV2ZGV2ZGV2ZGV2"` is base64 of a development session token seeded by `migrations/20260329000002_seed_dev_user.sql`. Cookie name is `session` (NOT `session_token`). The row exists **only** where `MYBIBLI_SEED_DEV_USERS` is set: on any other boot the seed gate deletes it along with the seeded users (issue #480), so never write a test — or a runbook — that assumes the token resolves on a production-shaped stack.
