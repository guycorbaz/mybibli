\chapter{Mise à jour et migration}
\label{ch:upgrade}

Les mises à jour de routine sont conçues pour être sûres.
L'exception est le saut 1.0.x → 1.1.0, un breaking change unique
documenté ci-dessous.

\section{Mises à jour de routine (1.y → 1.z)}

\begin{enumerate}
  \item Lisez les notes de version pour chaque version entre votre
        version courante et la cible.
  \item Prenez une \textbf{sauvegarde de base} fraîche
        (chapitre~\ref{ch:backup}).
  \item Mettez à jour le tag d'image dans
        \texttt{docker-compose.yml} (ou re-tirez \texttt{:latest}
        si vous suivez ce tag).
  \item Lancez \texttt{docker compose up -d}. Le nouveau conteneur
        boote, exécute les nouvelles migrations contre la base
        existante, et reprend le service.
  \item Surveillez les logs pour les erreurs de migration :
        \texttt{docker compose logs mybibli | grep -i migrate}.
\end{enumerate}

Les migrations sont append-only — les changements de schéma sont
forward-compatibles. Une installation 1.4 mise à jour en 1.5 garde
toutes les lignes de 1.4 et applique les nouvelles tables /
colonnes sur place.

\begin{tip}
Pour les installations homelab, le tag Docker \texttt{:latest} est
un défaut raisonnable. Pour des montages production
(bibliothèque communautaire, association), épinglez une version
explicite pour qu'un \texttt{pull} non surveillé n'amène pas une
release sur laquelle vous n'avez pas lu les notes.
\end{tip}

\section{Sauter des versions intermédiaires}

Passer d'une installation bien plus ancienne (1.3.x par exemple)
directement à la version courante est supporté et sûr pour la
base. Le moteur de migrations applique toutes les migrations
non encore appliquées dans l'ordre des timestamps au boot,
quelle que soit la distance sautée. Les migrations de schéma
sont purement additives — aucun \texttt{DROP COLUMN}, aucun
\texttt{DROP TABLE} dans aucune release — et les quatre
backfills de données existants (le seed CSRF token de 1.1.0,
le nettoyage \texttt{manually\_edited\_fields} de 1.1.8, etc.)
sont idempotents.

Ce qui reste valable sur un saut multi-versions :

\begin{itemize}
  \item \textbf{Sauvegardez avant la mise à jour.} Il n'y a pas
        de rollback automatique. Une migration qui échoue en
        cours d'exécution laisse la base dans un état
        incohérent ; la voie de récupération est la sauvegarde
        pré-mise à jour (chapitre~\ref{ch:backup}).
  \item \textbf{Les couvertures JPG pré-1.1.4 sont perdues.}
        Jusqu'à 1.1.4, le volume \texttt{mybibli\_covers}
        n'était pas déclaré ; les couvertures écrites avant
        cette version étaient perdues à chaque upgrade de
        conteneur. Sauter directement vers 1.7 ne les récupère
        pas — re-fetch via l'action admin \textbf{Bulk re-fetch
        missing covers} (ajoutée en 1.2) ou le bouton
        \textbf{Re-fetch metadata} par titre.
  \item \textbf{Le premier boot peut prendre quelques minutes.}
        Un saut qui exécute 20+ migrations contre un gros
        catalogue est silencieux côté UX — attendez que
        \texttt{/health} réponde avant de vous inquiéter.
\end{itemize}

Le saut 1.0.x → 1.1.0 est l'unique exception qui nécessite la
procédure dédiée ci-dessous.

\section{Le saut 1.0.x → 1.1.0}\label{sec:upgrade-1.1.0}

\begin{warning}
\textbf{Ceci est un breaking change unique.}\index{mise à jour 1.1.0}
Les installations 1.0.x sont sujettes au bug documenté dans
\href{https://github.com/guycorbaz/mybibli/issues/173}{\#173} :
les migrations seed créent les identifiants \texttt{admin/admin}
et \texttt{librarian/librarian} à chaque installation neuve, y
compris en production, et contournent silencieusement l'assistant
de première mise en service.
\end{warning}

Le chemin recommandé dépend de si votre installation 1.0.x détient
des données réelles :

\subsection*{Si votre installation 1.0.x est vide (aucun titre catalogué)}

Le chemin le plus simple : effacer la base et réinstaller en 1.1.0+.

\begin{enumerate}
  \item Arrêter la pile : \texttt{docker compose down}.
  \item Supprimer le volume de base :
        \texttt{docker volume rm mybibli\_mybibli\_db\_data}
        (ou l'équivalent sur votre hôte —
        \texttt{docker volume ls} les liste).
  \item Tirer l'image 1.1.0 : \texttt{docker compose pull}.
  \item Mettre à jour le tag d'image dans
        \texttt{docker-compose.yml} si vous aviez épinglé une
        version antérieure.
  \item Démarrer : \texttt{docker compose up -d}.
  \item Ouvrir \texttt{/setup} et parcourir l'assistant.
\end{enumerate}

\subsection*{Si votre installation 1.0.x détient des données réelles}

\begin{enumerate}
  \item Prenez une sauvegarde de base (chapitre~\ref{ch:backup}).
  \item Prenez une sauvegarde covers + \texttt{.env}.
  \item Connectez-vous comme l'admin seedé et changez le mot de
        passe \emph{avant} la mise à jour. La mise à jour 1.1.0
        elle-même est sûre, mais la rotation ferme la dernière
        fenêtre pendant laquelle les identifiants par défaut
        pourraient fuiter.
  \item Mettre à jour le tag d'image dans
        \texttt{docker-compose.yml} et lancer
        \texttt{docker compose up -d}.
  \item Le boot 1.1.0 détecte l'admin existant et n'active
        \emph{pas} l'assistant — l'admin avec mot de passe tourné
        reste l'admin actif.
\end{enumerate}

\subsection*{La nouvelle variable \texttt{MYBIBLI\_SEED\_DEV\_USERS}}

À partir de 1.1.0, la migration seed est gardée par
\texttt{MYBIBLI\_SEED\_DEV\_USERS}\index{MYBIBLI\_SEED\_DEV\_USERS}.
Le défaut est \texttt{0} (pas de seed). Ne la positionnez à
\texttt{1} que pour des flux de dev local ou des tests automatisés
— jamais en production. L'assistant de première mise en service
devient le chemin canonique d'onboarding.

\section{Lire les notes de version}

Chaque release mybibli publie une page GitHub Release avec :

\begin{itemize}
  \item un paragraphe résumant le changement ;
  \item l'impact migration (aucun / additif / breaking) ;
  \item un lien vers le diff contre le tag précédent ;
  \item les PDF de ce manuel (anglais + français) en pièce jointe
        une fois le build PDF de release câblé dans la CI.
\end{itemize}

Lisez les notes avant de mettre à jour. Les breaking changes
portent une étiquette \emph{Breaking} bien visible.

\section{Nouveautés de la 1.14.0}\label{sec:whats-new-1.14.0}

La version 1.14.0 est une mineure de fonctionnalités sur la 1.13.0.
Elle corrige trois défauts du flux de catalogage et étend
l'enrichissement bibliographique aux ouvrages anglophones.
\emph{Aucune migration de base — la mise à jour se réduit à un
échange d'image sur un schéma inchangé, et le retour arrière vers la
1.13.0 reste propre.} \texttt{docker compose pull \&\& docker compose
up -d} de routine.

\subsection*{Corrections du catalogage}

\begin{itemize}
  \item \textbf{\#440 \string— l'étiquette de volume se rattachait au
        mauvais titre.} Lorsque plusieurs articles identifiés par un
        code UPC (typiquement des CD) étaient catalogués à la suite
        dans une même session de navigation, seul le premier
        établissait correctement le contexte de scan. Les suivants
        laissaient le titre précédent actif : l'étiquette scannée
        ensuite se rattachait à ce titre-là, ou échouait avec un
        message trompeur si celui-ci avait été supprimé entre-temps.
        Tous les chemins de scan passent désormais par une même
        activation de contexte.
  \item \textbf{\#441 \string— message d'erreur trompeur.} Quand le
        titre actif avait été supprimé, le scan d'une étiquette
        répondait « Introuvable », ce qui désignait l'étiquette alors
        que le problème était l'absence d'article actif. Le message
        indique maintenant qu'aucun article n'est sélectionné, et le
        contexte périmé est effacé pour que le scan suivant reparte
        sur des bases saines.
  \item \textbf{\#442 \string— étiquette bloquée après suppression.}
        Supprimer un volume ne libérait pas son code~V : il fallait
        passer par la corbeille et une suppression définitive avant de
        pouvoir recoller l'étiquette sur un autre ouvrage, et le
        message d'erreur désignait le propriétaire par un
        « \texttt{?} ». L'étiquette est désormais réutilisable
        directement. Les informations propres à l'ancien exemplaire
        (état, emplacement, prix d'achat, valeur) sont écartées
        puisqu'il s'agit d'un autre objet physique, et consignées
        dans le journal d'audit. La réutilisation est refusée lorsque
        le volume supprimé porte un historique de prêts, car elle
        rattacherait cet historique à un exemplaire différent.
\end{itemize}

\subsection*{Zones bibliographiques pour les ouvrages anglophones}

\begin{itemize}
  \item \textbf{\#439 \string— la Library of Congress complète la
        BnF.} Les six champs alignés UNIMARC introduits en 1.13.0
        restaient vides sur les ouvrages anglophones : la BnF ne les
        catalogue pas, et les autres sources ne portent aucune donnée
        bibliographique structurée. mybibli interroge désormais aussi
        les notices \textbf{MARC~21} de la Library of Congress.
  \item \textbf{Complémentarité champ par champ.} Lorsque la source
        qui a résolu un titre ne renseigne qu'une partie des six
        zones, l'autre bibliothèque est consultée pour compléter
        celles restées vides. Une valeur déjà présente n'est jamais
        écrasée.
  \item \textbf{Portée réelle.} Seuls les ouvrages à préfixe ISBN
        9780 et 9781 sont concernés. \emph{Les titres français que la
        BnF n'a pas su décrire resteront vides} : la Library of
        Congress ne les connaît pas davantage. Tenez-en compte en
        lisant les chiffres du complément de métadonnées après la
        mise à jour.
  \item \textbf{Bouton renommé.} L'action de l'onglet Santé s'appelle
        désormais \emph{Compléter les métadonnées via les
        bibliothèques}, puisqu'elle ne s'appuie plus sur la seule
        BnF.
\end{itemize}

\section{Nouveautés de la 1.13.0}\label{sec:whats-new-1.13.0}

La version 1.13.0 est une mineure de fonctionnalités sur la 1.12.0,
centrée sur un thème : l'alignement du catalogue sur la norme
bibliographique \textbf{UNIMARC}. \emph{Une migration de base
automatique et additive — aucune action opérateur.} \texttt{docker
compose pull \&\& docker compose up -d} de routine.

\begin{itemize}
  \item \textbf{\#389 \string— champs de catalogage alignés
        UNIMARC.} Les titres portent désormais six champs
        bibliographiques supplémentaires, mappés sur leurs zones
        UNIMARC : mention de responsabilité (200\$f), mention
        d'édition (205\$a), titre et numéro de collection
        (225\$a/\$v), note générale (300\$a) et titre original
        (500\$a). Ils sont capturés automatiquement depuis la BnF au
        scan d'un livre, et affichés sur la fiche titre dès qu'ils
        sont renseignés. La table de correspondance de référence est
        livrée dans le dépôt (\texttt{docs/unimarc-mapping.md}) ;
        l'import/export de notices (ISO~2709 / UNIMARC XML) fera
        l'objet d'un chantier ultérieur distinct.
  \item \textbf{Nouvelle action de l'onglet Santé :
        \emph{Compléter les métadonnées via BnF}.} Relance la
        recherche de métadonnées pour chaque titre déjà catalogué
        disposant d'un code, remplissant les nouveaux champs UNIMARC
        (et tout ce que les fournisseurs ont appris depuis) sans
        jamais écraser une valeur modifiée à la main. Partage le
        rythme, le back-off anti-blocage et le verrou d'exécution
        unique du re-fetch de couvertures.
  \item \textbf{\#434 \string— résumé de catalogage dans les
        journaux.} Chaque résolution de métadonnées journalise
        désormais une ligne \texttt{info} de synthèse (couverture
        trouvée ? combien de champs UNIMARC remplis ?), ce qui rend
        une exécution de complément facile à auditer depuis le
        fichier de log.
\end{itemize}

La version 1.12.0 est une mineure de fonctionnalités à 2 tickets sur

\texttt{docker compose pull \&\& docker compose up -d} de routine.

\begin{itemize}

  \item Corrigé au passage : les couvertures servies par des hôtes
        sans TLS (p.\,ex.\ un serveur d'images local au LAN) ne
        échouent plus au téléchargement.
\end{itemize}

\section{Nouveautés de la 1.11.0}\label{sec:whats-new-1.11.0}

La version 1.11.0 regroupe les quatre problèmes remontés par la revue
des journaux de production de juillet — deux corrections de bugs et
deux améliorations côté opérateur. \emph{Une migration additive de
paramètres ; appliquée automatiquement — aucune action opérateur.}
\texttt{docker compose pull \&\& docker compose up -d} de routine.

\begin{itemize}
  \item \textbf{\#418 \string— les sessions survivent au verrouillage
        d'écran d'une tablette.} Le cookie de session est désormais
        persistant (sa durée de vie suit le délai d'inactivité) au lieu
        d'un cookie de session navigateur : les iPads et autres
        appareils qui jettent les cookies de session au verrouillage ne
        vous déconnectent plus en plein catalogage. Le délai
        d'inactivité lui-même se règle désormais en heures (1--720,
        défaut 4) dans \texttt{/admin > System > Sessions} — voir
        \autoref{sec:system}.
  \item \textbf{\#419 \string— le re-fetch de couvertures en lot
        récupère vraiment des couvertures.} L'action \emph{Récupérer
        les couvertures manquantes} espace désormais ses requêtes
        (délai configurable, défaut 1\,s par titre), retente les
        consultations bloquées avec un délai croissant, et se termine
        par un résumé sur l'onglet Santé — couvertures récupérées,
        erreurs fournisseur, et titres sans couverture disponible nulle
        part. Auparavant, une exécution en rafale déclenchait le
        blocage anti-rafale de Google Books et ne récupérait
        silencieusement rien.
  \item \textbf{\#416 \string— l'auto-purge quotidienne débloquée.}
        Des lignes de session résiduelles pointant vers un utilisateur
        désactivé de longue date ne bloquent plus la purge définitive à
        30 jours de cet utilisateur (une erreur quotidienne dans les
        journaux depuis juin). La purge nettoie désormais ces lignes
        elle-même.
  \item \textbf{\#417 \string— des journaux plus silencieux.} Cliquer
        les puces \emph{Lacunes} du tableau de bord n'émet plus une
        ligne d'avertissement parasite à chaque clic.
\end{itemize}

\section{Notes des versions antérieures}

Les notes des versions 1.9.0 et antérieures sont publiées sur la page
GitHub Releases du projet
(\url{https://github.com/guycorbaz/mybibli/releases}), une entrée par

\section{Rollback}

Le rollback \emph{n'est pas} un flux de première classe. Les
migrations de schéma avancent uniquement — il n'y a pas de
\texttt{down.sql}. La stratégie de récupération supportée est :

\begin{enumerate}
  \item Restaurer la sauvegarde de base pré-mise-à-jour
        (chapitre~\ref{ch:backup}).
  \item Réépingler le tag d'image à la version antérieure.
  \item Démarrer la pile.
\end{enumerate}

Cela fonctionne car la sauvegarde est cohérente avec le schéma
antérieur. Tenter de pointer une image plus ancienne sur une base
fraîchement migrée échoue au boot.
