\chapter{Sauvegarde et restauration}
\label{ch:backup}

Une bibliothèque auto-hébergée n'a pas de filet de sécurité dans le
cloud. Ce chapitre couvre quoi sauvegarder, à quelle fréquence, et
comment restaurer.

\section{Quoi sauvegarder}

Trois artefacts forment ensemble une sauvegarde mybibli complète :

\begin{enumerate}
  \item \textbf{La base MariaDB.}\index{sauvegarde!base} Contient
        chaque titre, volume, lieu, contributeur, prêt,
        utilisateur, journal d'audit et paramètre. La perdre,
        c'est repartir de zéro.
  \item \textbf{Les images de couverture.}\index{sauvegarde!couvertures}
        Téléchargées au catalogage et persistées dans le volume
        Docker \texttt{mybibli\_covers} (ou dans le chemin hôte du
        bind mount si vous avez basculé selon
        section~\ref{sec:install-covers-bind}). Les perdre, le
        catalogue fonctionne toujours mais chaque page de titre
        affiche un placeholder générique tant que vous n'avez pas
        re-fetché les métadonnées titre par titre (issue~\#213 — les
        installs antérieures à 1.1.4 sans ce volume perdaient les
        couvertures à chaque mise à jour du conteneur). Le même
        volume contient, dans un dossier caché \texttt{.staging},
        les couvertures proposées par des agents IA et pas encore
        décidées (section~\ref{sec:agents-staging}).
  \item \textbf{Le fichier \texttt{.env}.}\index{sauvegarde!.env}
        Contient les mots de passe (base, clés d'API non encore
        migrées). Le perdre, un re-déploiement vous oblige à
        re-saisir chaque credential.
\end{enumerate}

Les images Docker elles-mêmes ne sont \emph{pas} critiques — vous
pouvez toujours les re-tirer depuis Docker Hub.

\section{Sauvegardes}
\label{sec:backups}

Depuis 1.29.0, mybibli écrit lui-même une sauvegarde, à la demande
depuis \textbf{Admin → Sauvegardes}\index{sauvegarde!onglet Sauvegardes}
ou selon un calendrier, et en restaure une depuis le même onglet
(section~\ref{sec:backups-restore}). Un seul fichier contient toute la
base et toutes les couvertures : la bibliothèque peut être récupérée,
ou chargée ailleurs, sans restaurer tout MariaDB. Les procédures de la
fin de ce chapitre (à partir de \emph{Procédure de sauvegarde}) restent
valables ; celle-ci est plus simple.

\subsection*{Monter le dossier de sauvegarde}

mybibli écrit dans \texttt{/app/backups} à l'intérieur du conteneur
(la variable \texttt{MYBIBLI\_BACKUP\_DIR} le change). Il \emph{ne crée
jamais ce dossier} : c'est vous qui le montez. Le
\texttt{docker-compose.yml} livré avec 1.29.0 contient la ligne ; sur
un fichier plus ancien, ajoutez-la sous les \texttt{volumes:} du
service \texttt{mybibli} puis redémarrez :

\begin{lstlisting}
    volumes:
      - ./backups:/app/backups
\end{lstlisting}

Une nouvelle installation suit l'étape~1d du
chapitre~\ref{ch:installation} (section~\ref{sec:install-backups}). La
ligne en place, Docker crée lui-même le dossier \texttt{backups/} de
l'hôte, à côté de \texttt{docker-compose.yml}, au premier démarrage
s'il n'existe pas.

L'onglet montre le dossier et son état : \emph{prêt}, \emph{absent}
(pas de montage : la ligne manque, ou \texttt{MYBIBLI\_BACKUP\_DIR}
désigne un autre chemin) ou \emph{non accessible en écriture} (donnez
au compte du conteneur le droit d'écrire dans le dossier de l'hôte ; un
partage réseau monté en lecture seule donne aussi cet état). Tant que
le dossier n'est pas prêt, une sauvegarde est refusée avec cette raison
et rien n'est écrit nulle part. L'onglet Santé affiche le même
avertissement, qui commence par « Attention : ».

\textbf{Un dossier par instance.} Donnez à chaque instance de mybibli
son propre dossier de sauvegarde. Une instance de test ne doit jamais
écrire dans le dossier de la bibliothèque en production : deux
instances qui partagent un dossier effacent mutuellement leurs fichiers
temporaires et, si elles partagent aussi un identifiant d'instance (une
copie chargée ailleurs le conserve), appliquent chacune leur rotation
aux sauvegardes de l'autre.

\subsection*{Écrire une sauvegarde}

Cliquez sur \textbf{Sauvegarder maintenant}. La réponse s'affiche sous
le bouton, par exemple \emph{Sauvegarde écrite :
mybibli-3f9c0a1b2c3d4e5f-20261125T070409Z.tar.gz (2.4 MiB, 812 titres,
640 couvertures).} Le nom porte l'\emph{identifiant d'instance} de la
bibliothèque (affiché dans l'onglet Santé, sous Versions) et l'heure
UTC. Une seule sauvegarde s'écrit à la fois ; un second clic pendant ce
temps est refusé. Le catalogue reste utilisable pendant la sauvegarde :
la base est lue dans un instantané cohérent, sans rien verrouiller. Une
sauvegarde qui échoue ne laisse rien derrière elle ; les journaux
disent pourquoi.

\subsection*{Sauvegardes automatiques et rotation}
\label{sec:backups-schedule}
\index{sauvegarde!automatique}\index{sauvegarde!rotation}

Le calendrier se règle dans \textbf{Admin → Système}, section
\textbf{Sauvegardes} :

\begin{itemize}
  \item \textbf{Sauvegarde automatique} --- \emph{Désactivée},
        \emph{Toutes les heures} (par défaut), \emph{Toutes les 2
        heures}, \dots, \emph{Toutes les 12 heures} ou \emph{Une fois
        par jour}. mybibli vérifie à cet intervalle et n'écrit une
        sauvegarde que si quelque chose a changé depuis la précédente :
        une bibliothèque au repos ne remplit pas le dossier.
  \item \textbf{Sauvegardes quotidiennes à garder} --- un nombre entier
        de 1 à 365, 14 par défaut (voir la rotation ci-dessous).
\end{itemize}

Cliquez sur \textbf{Enregistrer la sauvegarde automatique} ; la ligne
de confirmation reprend les deux valeurs. La première vérification a
lieu dix minutes après le démarrage de mybibli. « Rien n'a changé »
se mesure par rapport à la dernière sauvegarde écrite par mybibli
depuis son démarrage, automatique ou à la main : après un redémarrage,
la première vérification en écrit toujours une.

\textbf{Rotation.} Après chaque vérification et après chaque sauvegarde
écrite avec \textbf{Sauvegarder maintenant}, mybibli supprime les
sauvegardes dont il n'a plus besoin. Il garde :
\begin{itemize}
  \item toutes les sauvegardes des dernières 24 heures ;
  \item la plus récente, quel que soit son âge ;
  \item la dernière sauvegarde de chacun des derniers jours \emph{où une
        sauvegarde a été écrite}, autant de jours que l'indique
        \textbf{Sauvegardes quotidiennes à garder} (jours comptés dans
        le fuseau horaire de la bibliothèque).
\end{itemize}
Compter les jours où une sauvegarde a été écrite, et non les jours du
calendrier, garantit qu'une bibliothèque laissée de côté pendant un mois
conserve ses 14 dernières sauvegardes quotidiennes. Chaque fichier
\texttt{.sha256} suit sa sauvegarde. La rotation ne supprime que les
sauvegardes de cette instance (leur nom porte l'identifiant de cette
instance) ; \textbf{une sauvegarde d'une autre instance n'est jamais
supprimée}, ni
aucun autre fichier du dossier. Baisser \textbf{Sauvegardes quotidiennes
à garder} supprime les sauvegardes quotidiennes les plus anciennes à la
rotation suivante, dans l'heure avec le calendrier par défaut.

\textbf{Place nécessaire.} Chaque sauvegarde pèse à peu près la taille du
dossier des couvertures plus une copie compressée de la base. Avec les
réglages par défaut, comptez au pire 24 sauvegardes horaires et 14
quotidiennes ; bien moins les jours sans changement.

\textbf{Dans l'onglet Santé}, le bloc \textbf{Sauvegardes} montre la
dernière sauvegarde (lue dans le dossier), la prochaine vérification,
« La sauvegarde automatique est désactivée (Admin → Système). » le cas
échéant, si la dernière vérification n'a rien trouvé à sauvegarder, une
sauvegarde automatique en échec, la dernière restauration et les
avertissements sur le dossier. La section \emph{Surveillance de la
production} du même onglet est décrite à la
section~\ref{sec:health-watch}.

\subsection*{Ce que contient le fichier}

Le fichier \texttt{.tar.gz} contient, dans l'ordre :
\begin{itemize}
  \item \texttt{database.sql} — toutes les tables, corbeille comprise,
        avec l'historique des migrations ;
  \item \texttt{covers/} — toutes les images de couverture
        (\texttt{<chiffres>.jpg}) ; les couvertures proposées de
        \texttt{.staging} sont laissées de côté ;
  \item \texttt{manifest.json} — l'identifiant d'instance, la version
        de mybibli, le niveau de migration, la date, le nombre de
        lignes de chaque table et le SHA-256 de chaque élément.
\end{itemize}
À côté, \texttt{<nom>.sha256} permet de vérifier le fichier :
\begin{lstlisting}
sudo sh -c 'cd backups && sha256sum -c mybibli-*.tar.gz.sha256'
\end{lstlisting}

\textbf{Le fichier est sensible.}\index{sauvegarde!sensible} Il
contient les empreintes des mots de passe des utilisateurs, celles des
clés d'API et les clés des fournisseurs de l'onglet Système. Il ne
contient pas les sessions ouvertes : leur table est sauvegardée vide
et aucun jeton de session n'est conservé,
si bien qu'après le chargement ou la restauration d'une sauvegarde,
chacun se reconnecte. mybibli
l'écrit avec le mode \texttt{0600} (lisible par son seul propriétaire)
; gardez le dossier de l'hôte, et chaque copie que vous en faites,
tout aussi privés.

\textbf{À qui appartiennent les fichiers.} L'image livrée tourne en
\texttt{root} : sur l'hôte, les sauvegardes appartiennent à
\texttt{root}, et seul \texttt{root} peut les lire. Copiez-les avec
\texttt{sudo} (ou en administrateur du NAS), fermez le dossier lui-même
aux autres comptes (\texttt{sudo chmod 700 backups}), ne le publiez pas
comme partage réseau ouvert à tous, et chiffrez la copie gardée hors
site (disque USB, stockage en ligne). Les fichiers \texttt{.sha256} ne
contiennent rien de secret.

\subsection*{Charger une sauvegarde dans une base de test}
\label{sec:backups-test-db}

\texttt{database.sql} est un dump standard : le client \texttt{mariadb}
le charge dans une base vide, pour une copie de test ou pour travailler
sur des données réelles (par exemple essayer une modification qui
réécrit des données sur tout le catalogue avant de la livrer, règle~\#20
du projet) :
\begin{lstlisting}
sudo tar -xzf backups/mybibli-<id>-<date>.tar.gz database.sql
mariadb -u root -p -e "CREATE DATABASE mybibli_copie"
sudo cat database.sql | mariadb -u root -p mybibli_copie
sudo rm database.sql
\end{lstlisting}
La copie est au niveau de migration de la sauvegarde ; un mybibli
démarré dessus la met à jour. Une telle instance de test reçoit son
propre dossier de sauvegarde (jamais celui de la production, voir
\emph{Un dossier par instance} plus haut). Les clés des fournisseurs de
l'onglet Système viennent avec le dump : effacez-les sur l'instance de
test si elle ne doit pas s'en servir.

\subsection*{Une couverture écrite pendant la sauvegarde}

Les couvertures sont copiées après la base. Une couverture téléchargée
dans les secondes qui séparent les deux peut se trouver dans le fichier
sans son titre, ou manquer pour un titre qui la cite. Le contrôle des
couvertures (section~\ref{sec:cover-check}) signale et répare les deux
cas, à une exception près : le fichier d'un titre créé pendant la
sauvegarde porte un numéro que la base sauvegardée n'avait pas encore
attribué ; après la restauration de cette sauvegarde, la réparation
reste donc bloquée jusqu'à ce que de nouveaux titres dépassent ce
numéro (\emph{Quand la bibliothèque semble être une autre base}, dans la
même section).

\section{Restaurer une sauvegarde}
\label{sec:backups-restore}
\index{sauvegarde!restauration}\index{restauration}

Une restauration remet toute la bibliothèque --- titres, volumes, prêts,
utilisateurs, réglages et couvertures --- dans l'état où elle était
lorsqu'une sauvegarde a été écrite. Elle se fait par un Admin depuis
\textbf{Admin → Sauvegardes}, à partir d'une sauvegarde présente
\emph{dans le dossier de sauvegarde} : mybibli ne téléverse ni ne
télécharge de sauvegarde.

\subsection*{Pas à pas}

\begin{enumerate}
  \item Ouvrez \textbf{Admin → Sauvegardes}. Sous \textbf{Sauvegarder
        maintenant}, la liste \textbf{Sauvegardes présentes dans le
        dossier} montre chaque sauvegarde, la plus récente en premier :
        \textbf{Date} (fuseau horaire de la bibliothèque),
        \textbf{Origine} (\emph{Cette instance} ou \emph{Autre instance
        (\dots)} avec son identifiant), \textbf{Taille} et une
        \textbf{Remarque} :
        \begin{itemize}
          \item \emph{Pas de fichier de contrôle} --- le fichier
                \texttt{.sha256} manque ; la restauration sera refusée
                tant que vous ne l'aurez pas copié à côté de la
                sauvegarde ;
          \item \emph{Illisible} --- le conteneur ne peut pas lire le
                fichier (voir \emph{À qui appartiennent les fichiers}
                plus haut) ;
          \item \emph{Supprimée à la prochaine rotation} --- une
                ancienne sauvegarde de cette instance que la rotation
                va effacer (voir \emph{Une sauvegarde copiée à la main}
                ci-dessous).
        \end{itemize}
  \item Cliquez sur \textbf{Restaurer…} sur la ligne. mybibli lit
        d'abord tout le fichier et le contrôle (sa somme de contrôle,
        chacun de ses éléments, sa version). Un fichier qui échoue à un
        contrôle n'ouvre aucune fenêtre : la raison s'affiche dans
        l'onglet, sous \textbf{Sauvegarder maintenant}, et se termine
        toujours par « Rien n'a été modifié. »
  \item La fenêtre \textbf{Restaurer cette sauvegarde ?} donne les faits
        --- date, origine, version de mybibli, taille, nombre de titres
        et de couvertures dans la sauvegarde et dans la bibliothèque
        actuelle --- et ce qui va suivre : toute la bibliothèque est
        remplacée, tout ce qui a été saisi depuis cette sauvegarde
        disparaît de la bibliothèque, une sauvegarde de sécurité de
        l'état actuel est écrite d'abord, mybibli ne répond à personne
        pendant une minute ou deux, et tout le monde est déconnecté
        ensuite. Une sauvegarde d'une autre instance, ou d'une version
        plus ancienne, ajoute chacune une ligne (voir plus bas).
  \item Cliquez sur \textbf{Restaurer cette sauvegarde}. Le bouton
        indique « Restauration en cours… Cela prend une minute ou deux ;
        gardez cette page ouverte. » Pendant ce temps, toutes les autres
        pages répondent par une page \emph{Maintenance} (« mybibli
        restaure une sauvegarde\dots ») ; les couvertures ne sont pas
        servies non plus.
  \item À la fin, la fenêtre indique \emph{Sauvegarde \dots{} restaurée
        (\dots{} titres, \dots{} couvertures). La sauvegarde de sécurité
        de l'état précédent est \dots. Tout le monde a été déconnecté.}
        Cliquez sur \textbf{Se reconnecter} et connectez-vous --- avec
        un compte de la bibliothèque \emph{restaurée}.
  \item Vérifiez le résultat : quelques titres, l'onglet Santé
        (\emph{Dernière restauration : \dots, depuis \dots{} (sauvegarde
        de sécurité : \dots).}) et le dossier de sauvegarde : le fichier
        \texttt{.restore-\allowbreak in-\allowbreak progress.json} doit avoir disparu (voir
        \emph{Après la restauration} ci-dessous).
\end{enumerate}

\textbf{La sauvegarde de sécurité} est une sauvegarde ordinaire de cette
instance, écrite juste avant que la bibliothèque soit remplacée et
nommée dans le message final. La restaurer annule la restauration. Elle
suit la rotation comme les autres (gardée au moins 24 heures).

\textbf{Une sauvegarde plus ancienne} (écrite par une version antérieure
de mybibli) est restaurée, puis mise à jour par les migrations, comme
lors d'une mise à jour. \textbf{Une sauvegarde plus récente} est
refusée : mettez d'abord mybibli à jour vers cette version.

\subsection*{Si la restauration est refusée}

Un refus ne modifie rien. Les plus courants :
\begin{itemize}
  \item \emph{son contenu ne correspond pas à sa somme de contrôle} ---
        le fichier est endommagé ou a été copié en partie : copiez-le à
        nouveau depuis son origine, ou prenez une autre sauvegarde ;
  \item \emph{son fichier de contrôle \dots.sha256 est absent} ---
        copiez le fichier \texttt{.sha256} à côté de la sauvegarde ;
  \item \emph{écrite par une version plus récente de mybibli} ---
        mettez d'abord mybibli à jour ;
  \item \emph{mybibli ne peut pas lire \dots} --- donnez au compte du
        conteneur le droit de lire le fichier ;
  \item \emph{n'est pas une sauvegarde que cette version de mybibli
        peut restaurer} --- le fichier porte le nom d'une sauvegarde,
        mais n'en a pas le contenu ;
  \item \emph{Une sauvegarde ou une restauration est déjà en cours} ---
        attendez une minute (une sauvegarde automatique peut être en
        cours) ;
  \item \emph{pendant le téléchargement des couvertures ou des
        métadonnées de toute la bibliothèque} --- attendez la fin du
        traitement affiché dans l'onglet Santé ;
  \item \emph{d'autres requêtes étaient encore en cours après 30
        secondes} --- réessayez dans un instant ;
  \item \emph{n'a pas pu écrire d'abord une sauvegarde de sécurité} ---
        le dossier est plein ou non accessible en écriture ; la raison
        suit.
\end{itemize}

Si la restauration elle-même échoue après avoir commencé (une
instruction de la sauvegarde qui ne se charge pas, par exemple), mybibli
remet la bibliothèque en état depuis la sauvegarde de sécurité et le
dit : \emph{La restauration a échoué ; mybibli a remis la bibliothèque
dans l'état où elle était juste avant\dots} Les journaux disent
pourquoi.

\subsection*{Derrière un reverse proxy}

La page qui lance la restauration attend sa fin, une minute ou deux sur
une grande bibliothèque. Un reverse proxy (Traefik, nginx, celui de
Synology) qui coupe les requêtes au bout de 60 secondes affiche
\emph{Erreur serveur (504) --- veuillez réessayer.} dans la fenêtre alors
que \emph{la restauration continue}. Ne réessayez pas : attendez deux
minutes, rechargez la page
(la page \emph{Maintenance} s'affiche jusqu'à la fin), connectez-vous et
lisez la ligne \emph{Dernière restauration} de l'onglet Santé. Pour
éviter cette frayeur, portez le délai de lecture du proxy à cinq
minutes pour mybibli.

\subsection*{Après la restauration}

\begin{itemize}
  \item Tout le monde se reconnecte ; les comptes et les mots de passe
        sont ceux de la bibliothèque restaurée.
  \item Les réglages (fuseau horaire, clés des fournisseurs, calendrier
        des sauvegardes, délai de session, niveau de journalisation\dots)
        sont ceux de la sauvegarde. L'identifiant d'instance reste celui
        de cette instance.
  \item Le dossier des couvertures contient exactement les couvertures
        de la sauvegarde.
  \item Une sauvegarde prise avant la fin de l'assistant de première
        utilisation ne contient aucun Admin actif : l'assistant s'ouvre
        à nouveau, ou utilisez la trappe \texttt{MYBIBLI\_RESET\_ADMIN}
        (section~\ref{sec:reset-admin-password}).
  \item \textbf{Jetez un œil au dossier de sauvegarde.} Pendant une
        restauration, mybibli y garde un fichier
        \texttt{.restore-\allowbreak in-\allowbreak progress.json} et le supprime à la fin. S'il
        est encore là après une restauration réussie (la ligne d'audit
        et la suppression du journal ont toutes deux échoué ; voir les
        journaux), le prochain démarrage de mybibli le prendrait
        pour une restauration interrompue et remettrait la bibliothèque
        en état depuis la sauvegarde de sécurité, ce qui annulerait
        votre restauration. Une fois la bibliothèque restaurée vérifiée,
        supprimez ce fichier à la main :
\begin{lstlisting}
sudo rm backups/.restore-in-progress.json
\end{lstlisting}
\end{itemize}

\subsection*{Une sauvegarde copiée à la main}

Pour restaurer une sauvegarde gardée ailleurs, copiez le fichier
\texttt{.tar.gz} \emph{et} son \texttt{.sha256} dans le dossier de
sauvegarde ; il apparaît dans la liste à la prochaine ouverture de
l'onglet. Une ancienne sauvegarde de cette instance --- plus ancienne que
ce que garde la rotation --- porte la remarque \emph{Supprimée à la
prochaine rotation} : la prochaine vérification automatique l'efface
(dans l'heure par défaut). Restaurez-la tout de suite, ou mettez d'abord
\textbf{Sauvegarde automatique} sur \emph{Désactivée} (Admin → Système),
restaurez, puis rétablissez le réglage. Une fois la restauration
commencée, le fichier n'est plus nécessaire.

\subsection*{Une sauvegarde d'une autre instance}

Une sauvegarde dont le nom porte un autre identifiant d'instance est
listée comme \emph{Autre instance (\dots)}. La restaurer est permis ; la
fenêtre précise que ses comptes et mots de passe remplacent ceux de
cette instance : vous vous connectez ensuite avec un compte de la
bibliothèque restaurée. Cette instance garde son propre identifiant :
ses sauvegardes suivantes le portent.

mybibli ne supprime jamais la sauvegarde d'une autre instance, ni avant
ni après une restauration, et la rotation n'en tient pas compte.
\textbf{Supprimez-la à la main quand vous n'en avez plus besoin}, avec
son \texttt{.sha256}.

\subsection*{Déplacer la bibliothèque vers un autre NAS}
\label{sec:backups-move}

\begin{enumerate}
  \item Sur le nouveau NAS, installez mybibli --- la même version que
        sur l'ancien, ou une plus récente --- avec son dossier de
        sauvegarde (chapitre~\ref{ch:installation}), et passez
        l'assistant de première utilisation avec un compte Admin
        provisoire.
  \item Sur l'ancien NAS, cliquez sur \textbf{Sauvegarder maintenant}
        (ou prenez la sauvegarde la plus récente) et copiez le fichier
        \texttt{.tar.gz} et son \texttt{.sha256} dans le dossier de
        sauvegarde du nouveau NAS --- avec \texttt{sudo}, en les gardant
        privés.
  \item Sur le nouveau NAS, restaurez-la depuis \textbf{Admin →
        Sauvegardes}. Elle est listée comme \emph{Autre instance} : la
        bibliothèque, ses comptes et ses réglages remplacent les
        provisoires.
  \item Connectez-vous avec un compte de l'ancienne bibliothèque,
        puis vérifiez l'onglet Santé et quelques titres. Une fois
        satisfait, supprimez à la main la sauvegarde copiée.
\end{enumerate}
Les couvertures viennent avec la sauvegarde : rien d'autre n'est à
copier, sauf le fichier \texttt{.env} si vous voulez les mêmes mots de
passe pour la base (il n'est pas dans la sauvegarde).

\section{Restaurer à la main}
\label{sec:restore-by-hand}
\index{restauration!à la main}

Dans le cas rare où mybibli n'a pu ni restaurer une sauvegarde ni
remettre la bibliothèque en état, la page \emph{Maintenance} indique :
\emph{mybibli n'a pu ni restaurer une sauvegarde ni remettre la
bibliothèque en état. Demandez à la personne qui a installé mybibli de
restaurer à la main la sauvegarde \dots}, en nommant une sauvegarde de
sécurité. La même raison figure dans les journaux au niveau
\texttt{error}. Cette section s'adresse à cette personne.

\begin{enumerate}
  \item \textbf{Cherchez le fichier
        \texttt{.restore-\allowbreak in-\allowbreak progress.json}.} S'il
        n'est plus dans le dossier de sauvegarde, la restauration
        s'était en fait terminée : redémarrez mybibli
        (\texttt{docker compose restart mybibli}) et vérifiez la
        bibliothèque. Ne restaurez rien à la main --- cela annulerait la
        restauration.
  \item \textbf{Redémarrez une fois.} Si le journal est là, redémarrez
        mybibli : au démarrage, avant toute autre chose, il lit le
        journal et remet la bibliothèque en état depuis la sauvegarde de
        sécurité qu'il nomme. Si cela réussit, les journaux indiquent
        \emph{A restore was cut short; the library was put back from its
        safety backup} et mybibli démarre normalement.
  \item \textbf{Si cela échoue encore,} mybibli refuse de démarrer (les
        journaux indiquent \emph{Refusing to start: a restore was cut
        short}, et Docker le relance sans fin). Restaurez la sauvegarde
        de sécurité à la main, depuis le dossier qui contient
        \texttt{docker-compose.yml} (base embarquée ; le mot de passe
        root est \texttt{MYSQL\_ROOT\_PASSWORD} dans \texttt{.env}) :
\begin{lstlisting}
docker compose stop mybibli
sudo sh -c 'cd backups && sha256sum -c mybibli-<id>-<stamp>.tar.gz.sha256 \
    && tar -xzf mybibli-<id>-<stamp>.tar.gz database.sql'
docker compose exec -T db sh -c 'mariadb -u root -p"$MYSQL_ROOT_PASSWORD" \
    -e "DROP DATABASE $MYSQL_DATABASE;
        CREATE DATABASE $MYSQL_DATABASE CHARACTER SET utf8mb4;"'
sudo cat backups/database.sql | docker compose exec -T db \
    sh -c 'exec mariadb -u root -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"'
docker compose run --rm --no-deps --entrypoint sh mybibli -c \
    'mkdir /tmp/x && tar -xzf /app/backups/mybibli-<id>-<stamp>.tar.gz \
     -C /tmp/x && cp -a /tmp/x/covers/. /app/covers/'
sudo rm backups/database.sql backups/.restore-in-progress.json
docker compose start mybibli
\end{lstlisting}
        La ligne \texttt{run} utilise l'image de mybibli avec ses propres
        volumes : elle trouve les couvertures où qu'elles soient montées.
        Avec une base externe, lancez les deux commandes
        \texttt{mariadb} sur ce serveur.
  \item Reconnectez-vous (aucune session ne survit), vérifiez la
        bibliothèque, puis lancez le contrôle des couvertures
        (section~\ref{sec:cover-check}) : il liste les fichiers de
        couverture dont la bibliothèque restaurée ne se sert plus, et
        les supprime --- sauf s'il signale l'une de ses protections (même
        section).
\end{enumerate}

Ne restaurez de cette façon qu'une sauvegarde de cette instance --- la
sauvegarde de sécurité nommée par le message en est une. Une sauvegarde
d'une autre instance porte son identifiant dans la base ; restaurez-la
depuis l'onglet Sauvegardes, qui conserve l'identifiant de cette
instance.

\section{Contrôle des couvertures}
\label{sec:cover-check}
\index{couvertures!contrôle}\index{contrôle des couvertures}

Le dossier des couvertures et la base peuvent diverger : une base
restaurée seule (depuis une sauvegarde MariaDB du NAS, sans les
couvertures), un volume monté par erreur, ou des titres purgés de la
corbeille --- la purge laisse leurs fichiers de couverture derrière
elle. Le \textbf{Contrôle des couvertures}, au bas d'\textbf{Admin →
Sauvegardes}, trouve les deux sortes d'écart.

\begin{enumerate}
  \item Cliquez sur \textbf{Contrôler les couvertures}. Le contrôle ne
        modifie rien. Il liste :
        \begin{itemize}
          \item \textbf{Fichiers de couverture qu'aucun titre ne
                possède} --- un fichier \texttt{<numéro>.jpg} à la
                racine du dossier des couvertures dont le numéro n'est
                celui d'aucun titre, ni actif ni dans la corbeille (nom,
                taille, date) ;
          \item \textbf{Titres dont le fichier de couverture manque} ---
                les titres qui désignent un fichier de couverture à eux
                absent du dossier, chacun lié à sa page, avec une
                remarque quand il est traité autrement : \emph{dans la
                corbeille} (l'adresse est effacée, rien n'est
                téléchargé), \emph{choisie à la main : téléversez-la à
                nouveau}, \emph{ni ISBN, ni ISSN, ni UPC : rien à
                télécharger}, \emph{une proposition de couverture est en
                attente : acceptez-la pour installer une couverture}
                (laissé tel quel).
        \end{itemize}
        Chaque liste montre ses 50 premières lignes. Tout le reste du
        dossier --- le dossier \texttt{.staging} des couvertures
        proposées, les fichiers temporaires, tout autre nom --- n'est
        jamais touché, seulement compté (\emph{Laissés tels quels :
        \dots}). Quand tout va bien : \emph{Les couvertures et la
        bibliothèque concordent : \dots{} fichiers de couverture
        contrôlés, rien à réparer.}
  \item Cliquez sur \textbf{Réparer…}. La fenêtre \textbf{Réparer les
        couvertures ?} indique combien de fichiers seront supprimés,
        combien de titres perdent l'adresse de leur couverture manquante
        et combien d'entre eux sont mis en file pour un nouveau
        téléchargement, et qu'\emph{un fichier supprimé ne peut revenir
        que d'une sauvegarde}. Cliquez sur \textbf{Réparer}.
  \item La réponse donne les nombres. Chaque élément est contrôlé à
        nouveau juste avant d'être modifié ; un élément qui a changé
        depuis le contrôle est laissé tel quel et compté. Deux autres
        lignes peuvent suivre : des fichiers qui n'ont pas pu être
        supprimés (le dossier des couvertures n'est pas accessible en
        écriture : donnez au compte du conteneur le droit d'y écrire,
        puis contrôlez à nouveau), et une réparation interrompue parce
        qu'une restauration a commencé (contrôlez à nouveau une fois la
        restauration terminée). Les
        téléchargements passent par la file de réessai des
        métadonnées : une vingtaine de titres toutes les 5 minutes
        (section~\ref{sec:startup-repairs}). Chaque réparation est
        inscrite au journal d'audit.
\end{enumerate}

La réparation est refusée pendant une sauvegarde ou une restauration
(\emph{Une sauvegarde ou une restauration est déjà en cours\dots}) :
réessayez une minute plus tard.

\textbf{Le premier contrôle d'une bibliothèque existante} liste en
général beaucoup de fichiers qu'aucun titre ne possède : les couvertures
de tous les titres purgés de la corbeille depuis les débuts de la
bibliothèque. C'est attendu ; la réparation les supprime.

\textbf{Quand le dossier semble non monté.} Si plus de la moitié des
couvertures utilisées par la bibliothèque manquent, le contrôle affiche
ses listes mais ne propose aucune réparation et indique : \emph{\dots{}
Cela ressemble à un dossier des couvertures non monté ; mybibli ne
réparera donc rien.} Une réparation effacerait alors l'adresse de
couverture de la plupart des titres. Vérifiez le volume des couvertures
de l'installation (section~\ref{sec:install-covers-bind} et
\emph{Symptôme : chaque titre affiche le placeholder},
section~\ref{sec:troubleshoot-couvertures-manquantes}), redémarrez, puis
contrôlez à nouveau.

\textbf{Quand la bibliothèque semble être une autre base.} Si au moins
un fichier de couverture qu'aucun titre ne possède porte un numéro que
cette base de données n'a jamais attribué à un titre (un numéro
supérieur à celui de tous les titres qu'elle a créés), le contrôle ne
propose pas non plus de réparation et indique : \emph{\dots{} fichiers
de couverture portent un numéro que cette base de données n'a jamais
attribué à un titre. Cela ressemble à une base de données qui n'est pas
celle de ce dossier ; mybibli ne supprimera donc rien.} mybibli est
alors sans doute branché sur une autre base, ou sur une base vide, et
une réparation supprimerait les couvertures de la vraie bibliothèque.
Les fichiers laissés par des titres purgés de la corbeille ne
déclenchent pas cette protection : leurs numéros ont été attribués par
cette base, et ils restent réparables.

Après une restauration, un fichier de couverture portant un numéro que
la base restaurée n'a pas encore attribué peut rester --- une couverture
téléchargée pendant l'écriture de la sauvegarde, ou laissée par une
restauration à la main : elle bloque la réparation (par prudence) jusqu'à
ce que de nouveaux titres dépassent ce numéro. Attendez, ou mettez ce
seul fichier de côté si vous êtes sûr de vous. La protection ne
détecte pas non plus toutes les mauvaises bases : une base qui a déjà
attribué des numéros plus élevés que ceux de tous les fichiers de
couverture passe au travers. Avant de cliquer sur \textbf{Réparer…},
lisez les listes : les titres qu'elles nomment doivent être les
vôtres. Vérifiez la base
de données de l'installation (\texttt{.env},
section~\ref{sec:env-vars}), redémarrez, puis contrôlez à nouveau.

Aucune de ces deux protections ne se contourne : corrigez
l'installation, pas les fichiers. Ne
déplacez ou ne supprimez des fichiers de couverture à la main que si
vous savez avec certitude à quelle bibliothèque ils appartiennent ---
une sauvegarde (section~\ref{sec:backups}) contient tous les fichiers de
couverture de sa bibliothèque.

\section{Procédure de sauvegarde}

\subsection*{Base de données — MariaDB embarquée}

Depuis l'hôte qui exécute la pile compose :

\begin{lstlisting}
docker compose exec -T db sh -c 'exec mariadb-dump \
    -u root -p"$MYSQL_ROOT_PASSWORD" \
    --single-transaction --routines --triggers \
    "$MYSQL_DATABASE"' \
    > backups/mybibli-$(date +%Y%m%d-%H%M%S).sql
\end{lstlisting}

Le drapeau \texttt{--single-transaction} est important : il fait un
snapshot cohérent sans verrouiller les tables pendant la durée du
dump. \texttt{--routines --triggers} préserve les routines stockées
(mybibli n'en utilise pas pour l'instant, mais le drapeau est peu
coûteux et future-proof).

Compressez le dump si l'espace disque est une préoccupation :

\begin{lstlisting}
gzip backups/mybibli-*.sql
\end{lstlisting}

\subsection*{Base de données — MariaDB externe}

Lancez \texttt{mariadb-dump} directement contre le serveur externe.
Les utilisateurs DSM Synology peuvent aussi planifier une tâche
\emph{Hyper Backup} qui cible le paquet MariaDB — elle produit une
sauvegarde binaire qui se restaure plus vite qu'un dump SQL.

\subsection*{Couvertures et \texttt{.env}}

Pour un répertoire de couvertures monté en bind-mount sur l'hôte,
une simple archive \texttt{tar} suffit :

\begin{lstlisting}
tar czf backups/mybibli-files-$(date +%Y%m%d).tar.gz \
    .env "$COVERS_HOST_PATH"
\end{lstlisting}

Pour l'install par défaut (volume Docker nommé), sauvegardez le
volume via Docker — le chemin hôte d'un volume nommé varie selon la
version de Docker et n'est pas stable, donc n'essayez pas de le
\texttt{tar} directement. Compose préfixe le volume du nom du projet,
par défaut celui du dossier qui contient \texttt{docker-compose.yml} :
dans \texttt{/srv/mybibli}, c'est \texttt{mybibli\_mybibli\_covers}.
\texttt{docker volume ls | grep mybibli\_covers} donne le nom réel ;
utilisez-le ci-dessous.

\begin{lstlisting}
docker run --rm \
    -v mybibli_mybibli_covers:/source:ro \
    -v "$(pwd)/backups:/backup" \
    alpine \
    tar czf "/backup/mybibli-covers-$(date +%Y%m%d).tar.gz" -C /source .
tar czf "backups/mybibli-env-$(date +%Y%m%d).tar.gz" .env
\end{lstlisting}

Le conteneur \texttt{alpine} jetable monte le volume nommé en
lecture seule, le répertoire \texttt{backups/} hôte en écriture, et
écrit l'archive tar. Même forme pour restaurer — voir la section
Restauration plus bas.

\section{Cadence recommandée}

\begin{itemize}
  \item \textbf{Base et couvertures} — depuis la 1.29.0, la sauvegarde
        automatique (section~\ref{sec:backups-schedule}) couvre les
        deux, toutes les heures par défaut. Laissez-la active ; les
        dumps de ce chapitre ne servent que sans elle.
  \item \textbf{\texttt{.env}} — copiez-le à chaque modification ; il
        n'est pas dans les sauvegardes de mybibli.
  \item \textbf{Copie hors site} — au moins mensuelle. Copiez le
        dossier \texttt{backups/} (avec \texttt{sudo} : les fichiers
        appartiennent à root) vers un NAS distant, un disque USB que
        vous échangez ou un stockage en ligne, chiffré. Un incendie qui
        consume le serveur domestique ne doit pas aussi consumer vos
        sauvegardes.
\end{itemize}

\begin{tip}
Une sauvegarde qui n'a jamais été restaurée n'est pas une
sauvegarde. Une fois par trimestre, restaurez votre dernier dump
dans un environnement Docker jetable et vérifiez que les compteurs
de titres et de prêts correspondent à ce que rapporte
\texttt{/admin > Health} en production.
\end{tip}

\section{Procédure de restauration}

\subsection*{Base de données}

Pour le setup avec base embarquée :

\begin{lstlisting}
docker compose stop mybibli
docker compose exec -T db sh -c 'mariadb -u root -p"$MYSQL_ROOT_PASSWORD" \
    -e "DROP DATABASE $MYSQL_DATABASE;
        CREATE DATABASE $MYSQL_DATABASE CHARACTER SET utf8mb4;"'
zcat backups/mybibli-20260513-1200.sql.gz | docker compose exec -T db \
    sh -c 'exec mariadb -u root -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"'
docker compose start mybibli
\end{lstlisting}

Pour MariaDB externe, les mêmes commandes client \texttt{mariadb}
fonctionnent contre le serveur externe.

\subsection*{Couvertures et \texttt{.env}}

Pour un install bind-mount hôte :

\begin{lstlisting}
tar xzf backups/mybibli-files-20260513.tar.gz
\end{lstlisting}

Pour l'install par défaut (volume nommé), restaurez via un
conteneur jetable symétrique à la sauvegarde (même nom de volume que
plus haut) :

\begin{lstlisting}
docker compose stop mybibli
docker run --rm \
    -v mybibli_mybibli_covers:/target \
    -v "$(pwd)/backups:/backup:ro" \
    alpine \
    sh -c "rm -rf /target/* && tar xzf /backup/mybibli-covers-20260513.tar.gz -C /target"
tar xzf backups/mybibli-env-20260513.tar.gz
docker compose start mybibli
\end{lstlisting}

Redémarrez la pile pour que le conteneur mybibli prenne en compte
le \texttt{.env} restauré.

\section{Migration vers un nouvel hôte}

La procédure de sauvegarde est aussi la procédure de migration :

\begin{enumerate}
  \item Sur l'ancien hôte : produire un dump de base et une archive
        tar frais.
  \item Transférer les deux sur le nouvel hôte.
  \item Sur le nouvel hôte : installer Docker, récupérer le fichier
        compose depuis la release correspondant à la version du
        dump, placer \texttt{.env} et \texttt{covers/} à côté,
        restaurer la base, démarrer la pile.
  \item Vérifier en comptant les titres sur \texttt{/admin >
        Health} et en contrôlant quelques pages de titre au
        hasard.
\end{enumerate}

\begin{warning}
Le dump est lié à la version de \emph{schéma}. Si l'hôte source
tournait en 1.1.0 et que le nouvel hôte tire 1.5.0, les migrations
du nouvel hôte mettront à niveau la base restaurée — c'est OK.
L'inverse (restaurer un dump 1.5.0 sur une installation 1.1.0)
n'est \emph{pas} supporté et échouera au boot. Restaurez toujours
sur un hôte exécutant la même version mybibli ou plus récente.
\end{warning}
