\chapter{Upgrade and migration}
\label{ch:upgrade}

Routine upgrades are designed to be safe. The exception is the
1.0.x to 1.1.0 jump, which is a one-time breaking change documented
below.

\section{Routine upgrades (1.y to 1.z)}

\begin{enumerate}
  \item Read the release notes for every version between your
        current and the target version.
  \item Take a fresh \textbf{database backup} (chapter
        \ref{ch:backup}).
  \item Update the image tag in \texttt{docker-compose.yml} (or
        repull \texttt{:latest} if you track that tag).
  \item Run \texttt{docker compose up -d}. The new container boots,
        runs any new migrations against the existing database, and
        starts serving requests.
  \item Watch the logs for migration errors:
        \texttt{docker compose logs mybibli | grep -i migrate}.
\end{enumerate}

Migrations are append-only — schema changes are forward
compatible. A 1.4 install upgraded to 1.5 keeps every row from 1.4
and applies new tables / columns in place.

\begin{tip}
For homelab installs, the \texttt{:latest} Docker tag is a
reasonable default. For production-style setups (a community
library, an association), pin to an explicit version tag so an
unattended pull does not bring in a release you have not read about.
\end{tip}

\section{The 1.0.x to 1.1.0 jump}\label{sec:upgrade-1.1.0}

\begin{warning}
\textbf{This is a one-time breaking change.}\index{1.1.0 upgrade}
1.0.x installs are subject to the issue documented in
\href{https://github.com/guycorbaz/mybibli/issues/173}{\#173}:
the seed migrations create the credentials \texttt{admin/admin}
and \texttt{librarian/librarian} on every fresh install, including
production, and silently bypass the first-launch setup wizard.
\end{warning}

The recommended path depends on whether your 1.0.x install holds
real data:

\subsection*{If your 1.0.x install is empty (no titles cataloged)}

The simplest path: wipe the database and reinstall on 1.1.0+.

\begin{enumerate}
  \item Stop the stack: \texttt{docker compose down}.
  \item Remove the database volume:
        \texttt{docker volume rm mybibli\_mybibli\_db\_data}
        (or the equivalent volume name on your host —
        \texttt{docker volume ls} lists them).
  \item Pull the 1.1.0 image:
        \texttt{docker compose pull}.
  \item Update the image tag in \texttt{docker-compose.yml} if you
        pinned a previous version.
  \item Start: \texttt{docker compose up -d}.
  \item Open \texttt{/setup} and walk through the wizard.
\end{enumerate}

\subsection*{If your 1.0.x install holds real data}

\begin{enumerate}
  \item Take a database backup (chapter \ref{ch:backup}).
  \item Take a covers + \texttt{.env} backup.
  \item Log in as the seeded admin and rotate the password
        \emph{before} you upgrade. The 1.1.0 upgrade flow itself is
        safe, but rotation closes the only window where the default
        credentials could leak.
  \item Update the image tag in \texttt{docker-compose.yml} and run
        \texttt{docker compose up -d}.
  \item The 1.1.0 boot detects the existing admin and does
        \emph{not} re-enable the wizard — the rotated admin remains
        the active admin.
\end{enumerate}

\subsection*{The new \texttt{MYBIBLI\_SEED\_DEV\_USERS} variable}

Starting with 1.1.0, the seed migration is gated by
\texttt{MYBIBLI\_SEED\_DEV\_USERS}\index{MYBIBLI\_SEED\_DEV\_USERS}.
The default is \texttt{0} (no seed). Only set it to \texttt{1} for
local-development workflows or automated tests — never in
production. The first-launch wizard becomes the canonical
onboarding path.

\section{Reading the release notes}

Every mybibli release publishes a GitHub Release page with:

\begin{itemize}
  \item a one-paragraph summary of the change set;
  \item the migration impact (none / additive / breaking);
  \item a link to the diff against the previous tag;
  \item attached PDFs of this manual (English + French) once the
        release-time PDF build is wired into CI.
\end{itemize}

Read the notes before upgrading. Breaking changes are tagged with a
prominent \emph{Breaking} label.

\section{What's new in 1.7.1}\label{sec:whats-new-1.7.1}

Version 1.7.1 is a patch release that closes the v1.7.0 \#301 gap
and bundles four production-surfaced bugfixes from the user's
v1.7.0 NAS upgrade. \emph{No schema migration affecting catalog
data}; routine \texttt{docker compose pull \&\& docker compose up
-d}. One new settings row is seeded (\texttt{log\_level}) by an
idempotent migration.

Six fixes:

\begin{itemize}
  \item \textbf{Runtime log-level admin UI (\#308).} Finishes the
        v1.7.0 \#301 feature properly. \texttt{/admin > System}
        gains a \textbf{Logging} section with a free-form
        \texttt{EnvFilter} directive field. Click Save and the
        next log line uses the new level \string— no
        \texttt{docker compose up -d}, no restart. Persisted to
        the \texttt{settings} table so the choice survives
        container restarts. The v1.7.0 release notes had
        advertised this surface but only the env-var bootstrap +
        rotation actually shipped; this release ships the missing
        piece.
  \item \textbf{API-key permanent-delete 422 (\#309).} The
        \texttt{DELETE /admin/api-keys/\{id\}} handler was
        returning 422 Unprocessable Entity because it required a
        request-body form, but HTMX \texttt{hx-delete} puts form
        fields in the query string. Drop the body extractor; the
        CSRF middleware already validates the \texttt{X-CSRF-Token}
        header. Latent regression since v1.5.1 \#284.
  \item \textbf{Provider-health probe timeout configurable, default
        bumped 3 s \string→ 10 s (\#310).} The hardcoded 3 s
        probe timeout was too tight for typical home-NAS DNS + TLS
        handshake; every probe was timing out, making
        \texttt{/admin > Health} permanently red even when
        providers were reachable for the actual metadata-fetch
        path. New env var
        \texttt{MYBIBLI\_PROVIDER\_HEALTH\_TIMEOUT\_SECS}
        (default 10) lets ops bump to 20\string–30 s on fragile
        uplinks or down to 4\string–5 s on fast infra.
  \item \textbf{Bulk cover-refetch now actually re-queries
        providers (\#311).} The admin "Re-fetch missing covers"
        action was silently no-op'ing on cached titles because the
        metadata chain short-circuited on the cache hit set when
        the title was originally cataloged. New \texttt{force\_refresh}
        path invalidates the cache before re-running the chain,
        so Google Books / BDGest / etc. get re-asked for a cover
        URL. List-mode after HTMX search swap also restored
        (\#315).
  \item \textbf{DB pool size 10 \string→ 20 (\#312).} A transient
        \texttt{pool timed out while waiting for an open
        connection} was observed on the user's prod NAS during a
        64-title bulk-refetch. The sqlx default 10 was too tight
        for HTTP handlers + 3 always-on background tasks +
        concurrent admin HTMX polling + the per-title DB hits of
        the bulk worker. 20 gives comfortable headroom for
        single-household / small-association load.
  \item \textbf{Home filter chips: drop duplicate "Non classé"
        chip (\#314).} The home page was rendering both a "Non
        classé" chip (auto-generated from the placeholder genre
        row) and a "Sans genre" chip (the dedicated \#205
        affordance) \string— both returning the same titles.
        Strip the placeholder from the chip list; the dedicated
        chip remains.
\end{itemize}

\section{What's new in 1.6.1}\label{sec:whats-new-1.6.1}

Version 1.6.1 is a one-fix hotfix shipped hours after the v1.6.0 NAS
upgrade. Routine \texttt{docker compose pull \&\& docker compose up
-d}, no schema migration.

\textbf{Empty \texttt{parent\_id} on root-location edit no longer
400s (\#296).} Repro: tick the new "Emplacement organisationnel"
checkbox on a \emph{root} location, submit \string→ \texttt{400
Failed to deserialize form body: parent\_id: cannot parse integer
from empty string}. Worked fine on non-root locations.

Root cause is pre-existing \string— latent since the location-edit
feature shipped. The form's
\texttt{<select name="parent\_id"><option value="">None</option>\string…</select>}
submits \texttt{parent\_id=} (empty string) when the user keeps the
root option. \texttt{\#[serde(default)] Option<u64>} only
short-circuits \emph{absent} fields; an empty string still hits the
u64 parser, which bails. CR \#280 just gave users a new reason to
edit root locations, exposing the latent bug.

Fix mirrors the existing pattern for
\texttt{deserialize\_optional\_i32} /
\texttt{deserialize\_optional\_f64} in \texttt{routes::series}:

\begin{itemize}
  \item New \texttt{deserialize\_optional\_u64} helper treats
        \texttt{""} / whitespace / absent as \texttt{None}, parses
        non-empty values as u64.
  \item Wired to \texttt{CreateLocationForm.parent\_id},
        \texttt{UpdateLocationForm.parent\_id}, AND
        \texttt{VolumeEditForm.condition\_state\_id} (same
        \texttt{<option value="">\string—</option>} shape, same
        latent bug \string— picking "no condition" on a volume would
        have 400'd the same way).
\end{itemize}

12 new unit + form round-trip tests; new E2E spec walks through
create root \string→ edit \string→ tick organisationnel \string→
submit \string→ \texttt{/locations}. Earlier client-side workaround
that stripped the \texttt{name="parent\_id"} attribute in the
location-edit form to dodge the 422 was removed.

\section{What's new in 1.5.2}\label{sec:whats-new-1.5.2}

Version 1.5.2 is a one-fix hotfix on top of v1.5.1: the v1.5.0 \#243
valuation workflow was partially broken in production. Saving a
\emph{Purchase price} or \emph{Estimated current value} on a volume
landed the UPDATE (the totals on \texttt{/stats/value} and the
home indicator both reflected the new amount) but returned a 500
to the user, and every subsequent view of the affected volume
crashed.

Root cause: SQLx 0.8 can't decode a raw MariaDB
\texttt{DECIMAL(10,2)} into \texttt{Option<f64>} without the
\texttt{bigdecimal} / \texttt{rust\_decimal} feature flag. The
write side worked because the driver coerces \texttt{f64} into
\texttt{DECIMAL}; the read side didn't. The aggregation queries
(\texttt{/stats/value} totals) already used \texttt{CAST(SUM(...)
AS DOUBLE)} and were unaffected.

Fix: \texttt{VolumeModel::find\_by\_id} and
\texttt{find\_by\_label} now wrap the two DECIMAL columns with
\texttt{CAST(... AS DOUBLE)}. Two new \texttt{sqlx::test}
regression guards INSERT a volume with non-NULL valuation columns
and assert round-trip so the bug can't silently regress on a
future refactor.

No schema migration, no breaking changes \string— routine
\texttt{docker compose pull \&\& docker compose up -d}.

\section{What's new in 1.5.1}\label{sec:whats-new-1.5.1}

Version 1.5.1 is a five-fix production-hygiene patch shipped within
hours of the v1.5.0 NAS upgrade. No schema migrations, no breaking
changes \string— routine \texttt{docker compose pull \&\& docker
compose up -d}.

\begin{itemize}
  \item \textbf{Wish list PDF crash (\#281).} The v1.5.0 Dockerfile
        never received \texttt{COPY static/fonts/} when CR \#266
        landed the vendored DejaVu Sans TTFs, so
        \texttt{/wishlist/export.pdf} returned 500 in production.
        Fix: one line added to the Dockerfile.
  \item \textbf{Trash permanent-delete crashed on titles (\#282).}
        The 4 child FKs that reference \texttt{titles}
        (\texttt{volumes}, \texttt{title\_contributors},
        \texttt{title\_series}, \texttt{pending\_metadata\_updates})
        default to RESTRICT and MariaDB rejected the parent delete
        as soon as any child row referenced it \string— even
        soft-deleted children, because FK constraints don't consider
        \texttt{deleted\_at}. Fix: \texttt{TrashService::permanent\_delete}
        now opens a transaction and cascades through the FK-ordered
        children before deleting the parent.
  \item \textbf{Library valuation toggle was missing from
        \texttt{/admin?tab=system} (\#283).} The v1.5.0 \#243 added
        \texttt{default\_currency} + \texttt{show\_value\_indicators}
        in the settings table and the AppSettings cache but no UI
        was wired to flip them. Fix: a new "Library valuation"
        section on the System tab with a currency dropdown + the
        opt-in indicator checkbox.
  \item \textbf{No path to delete a revoked API key (\#284).} The
        v1.4.0 \#241 implementation deliberately preserved revoked
        rows for audit, but the list grew monotonically. Fix: a
        Delete button on revoked rows (UX-DR8 modal) calling a new
        \texttt{DELETE /admin/api-keys/\{id\}} handler. Active
        keys still show only Revoke. The audit references to
        deleted keys survive (the link is logical, not a schema
        FK).
  \item \textbf{Admin \string→ Health tab marked every provider
        red (\#285).} \texttt{probe\_once} was sending HEAD without
        a User-Agent and treating 4xx responses as "down" \string—
        most providers' WAFs answer 4xx to anonymous HEADs even
        when the API works. Fix: the probe now sends
        \texttt{User-Agent: mybibli/1.x.y} matching the actual
        metadata-fetch path and treats any HTTP response as
        Reachable (only timeouts / DNS / refused connections
        count as Unreachable).
\end{itemize}

\section{Rollback}

Rollback is \emph{not} a first-class flow. Schema migrations move
forward only — there is no \texttt{down.sql}. The supported recovery
strategy is:

\begin{enumerate}
  \item Restore the pre-upgrade database backup
        (chapter~\ref{ch:backup}).
  \item Pin the image tag back to the prior version.
  \item Start the stack.
\end{enumerate}

This works because the backup is consistent with the prior schema.
Trying to point an older image at a newly-migrated database will
fail to boot.
