\chapter{Upgrade and migration}
\label{ch:upgrade}

Routine upgrades are designed to be safe. The exception is the
1.0.x to 1.1.0 jump, which is a one-time breaking change documented
below.

\section{Routine upgrades (1.y to 1.z)}

\begin{enumerate}
  \item Read the release notes for every version between your
        current and the target version.
  \item Take a fresh \textbf{database backup} (chapter
        \ref{ch:backup}).
  \item Update the image tag in \texttt{docker-compose.yml} (or
        repull \texttt{:latest} if you track that tag).
  \item Run \texttt{docker compose up -d}. The new container boots,
        runs any new migrations against the existing database, and
        starts serving requests.
  \item Watch the logs for migration errors:
        \texttt{docker compose logs mybibli | grep -i migrate}.
\end{enumerate}

Migrations are append-only — schema changes are forward
compatible. A 1.4 install upgraded to 1.5 keeps every row from 1.4
and applies new tables / columns in place.

\begin{tip}
For homelab installs, the \texttt{:latest} Docker tag is a
reasonable default. For production-style setups (a community
library, an association), pin to an explicit version tag so an
unattended pull does not bring in a release you have not read about.
\end{tip}

\section{Skipping intermediate versions}

Going from a much older install (say, 1.3.x) directly to the
current release is supported and safe for the database. The
migration runner applies every pending migration in timestamp
order at boot, regardless of how many you skip. Schema
migrations are purely additive — no \texttt{DROP COLUMN}, no
\texttt{DROP TABLE} in any release — and the four data
backfills that exist (e.g. the 1.1.0 CSRF token seed, the
1.1.8 \texttt{manually\_edited\_fields} cleanup) are
idempotent.

What still applies on a multi-version jump:

\begin{itemize}
  \item \textbf{Back up before upgrading.} There is no automatic
        rollback. A migration that fails mid-execution leaves the
        database in an inconsistent state; the recovery path is the
        pre-upgrade backup (chapter~\ref{ch:backup}).
  \item \textbf{Pre-1.1.4 cover JPGs are gone.} Until 1.1.4 the
        \texttt{mybibli\_covers} volume was not declared, so cover
        images written before that version were lost on every
        container upgrade. Skipping straight to 1.7 does not
        recover them — re-fetch via the admin \textbf{Bulk
        re-fetch missing covers} action (added in 1.2) or the
        per-title \textbf{Re-fetch metadata} button.
  \item \textbf{The first boot may take a few minutes.} A jump
        that runs 20+ migrations against a large catalog is
        silent at the UX level — wait for \texttt{/health} to
        respond before worrying.
\end{itemize}

The 1.0.x to 1.1.0 jump is the one exception that needs the
dedicated procedure below.

\section{The 1.0.x to 1.1.0 jump}\label{sec:upgrade-1.1.0}

\begin{warning}
\textbf{This is a one-time breaking change.}\index{1.1.0 upgrade}
1.0.x installs are subject to the issue documented in
\href{https://github.com/guycorbaz/mybibli/issues/173}{\#173}:
the seed migrations create the credentials \texttt{admin/admin}
and \texttt{librarian/librarian} on every fresh install, including
production, and silently bypass the first-launch setup wizard.
\end{warning}

The recommended path depends on whether your 1.0.x install holds
real data:

\subsection*{If your 1.0.x install is empty (no titles cataloged)}

The simplest path: wipe the database and reinstall on 1.1.0+.

\begin{enumerate}
  \item Stop the stack: \texttt{docker compose down}.
  \item Remove the database volume:
        \texttt{docker volume rm mybibli\_mybibli\_db\_data}
        (or the equivalent volume name on your host —
        \texttt{docker volume ls} lists them).
  \item Pull the 1.1.0 image:
        \texttt{docker compose pull}.
  \item Update the image tag in \texttt{docker-compose.yml} if you
        pinned a previous version.
  \item Start: \texttt{docker compose up -d}.
  \item Open \texttt{/setup} and walk through the wizard.
\end{enumerate}

\subsection*{If your 1.0.x install holds real data}

\begin{enumerate}
  \item Take a database backup (chapter \ref{ch:backup}).
  \item Take a covers + \texttt{.env} backup.
  \item Log in as the seeded admin and rotate the password
        \emph{before} you upgrade. The 1.1.0 upgrade flow itself is
        safe, but rotation closes the only window where the default
        credentials could leak.
  \item Update the image tag in \texttt{docker-compose.yml} and run
        \texttt{docker compose up -d}.
  \item The 1.1.0 boot detects the existing admin and does
        \emph{not} re-enable the wizard — the rotated admin remains
        the active admin.
\end{enumerate}

\subsection*{The new \texttt{MYBIBLI\_SEED\_DEV\_USERS} variable}

Starting with 1.1.0, the seed migration is gated by
\texttt{MYBIBLI\_SEED\_DEV\_USERS}\index{MYBIBLI\_SEED\_DEV\_USERS}.
The default is \texttt{0} (no seed). Only set it to \texttt{1} for
local-development workflows or automated tests — never in
production. The first-launch wizard becomes the canonical
onboarding path.

\section{Reading the release notes}

Every mybibli release publishes a GitHub Release page with:

\begin{itemize}
  \item a one-paragraph summary of the change set;
  \item the migration impact (none / additive / breaking);
  \item a link to the diff against the previous tag;
  \item attached PDFs of this manual (English + French) once the
        release-time PDF build is wired into CI.
\end{itemize}

Read the notes before upgrading. Breaking changes are tagged with a
prominent \emph{Breaking} label.

\section{What's new in 1.17.0}\label{sec:whats-new-1.17.0}

Version 1.17.0 is a minor release on 1.16.0. \emph{No migration, no
operator action} \string— upgrade the image and restart.

Both changes came from the same reader, eight months apart, and neither
turned out to be the fault it was reported as. In both cases the
machinery was already doing the right thing and the screen was failing
to say so.

\begin{itemize}
  \item \textbf{\#202 \string— a failed lookup now tells you why.} When
        no library could describe a scanned book, mybibli said only that
        it had failed. That single sentence covered three situations
        that call for opposite reactions, and you had no way to tell
        them apart:

        \begin{itemize}
          \item every library was searched and none holds the book
                \string— nothing to be done, and no key or retry will
                change it. Type the details in by hand;
          \item a library was too busy or too slow to answer \string—
                genuinely worth pressing the button again in a few
                minutes;
          \item a library was never asked at all, because its access key
                is not filled in \string— one field in
                \emph{Administration \textrightarrow{} System}, and it
                is settled for good.
        \end{itemize}

        Open a title and press \emph{Re-download metadata}: the message
        underneath now names which of the three it was, and names the
        libraries concerned. Their names are never translated \string—
        they are the libraries' own.

        One case had to be repaired for this to be honest at all. OMDb
        and TMDb, with no access key entered, used to report exactly
        what they report after a fruitless search. They now say that
        they were not asked.
  \item \textbf{\#206 \string— which of genre and Dewey a lookup may
        overwrite.} The request was that the genre stop being
        overwritten by automatic metadata. It never was: no library in
        the chain supplies a genre, and nothing in mybibli writes one.
        What the form did not say is that the field beside it behaves
        the \emph{other} way round \string— the Dewey code \emph{is}
        offered by libraries, and goes on being offered until the day
        you correct it yourself, after which it is left alone as yours.

        Reading the form, one would naturally guess this the wrong way
        round. Both fields are now grouped in a \emph{Classification}
        section that states the difference in one line. The publication
        date, which describes the book rather than your shelving of it,
        stays outside.
\end{itemize}

\section{What's new in 1.16.0}\label{sec:whats-new-1.16.0}

Version 1.16.0 is a minor release on 1.15.0. \emph{No migration, no
operator action} \string— upgrade the image and restart.

\begin{itemize}
  \item \textbf{\#450 \string— a third library describing your
        English-language books.} Some titles stayed bare however often
        you asked: neither the French National Library nor the Library
        of Congress holds them. mybibli now also consults
        \emph{K10plus}, the shared catalogue of the German academic
        libraries, purely to fill in the bibliographic fields the
        first answering library left empty. On the collection it was
        measured against, it filled more of them than any other
        source, including for English titles published in Britain and
        the United States \string— German university libraries hold a
        great deal of anglophone technical publishing. \textbf{To
        benefit from it on titles already catalogued}, run
        \emph{Backfill metadata} once from
        \emph{Administration \textrightarrow{} Health} after
        upgrading; new scans use it automatically.

        A caveat worth stating plainly: a residue of titles remains
        that no consulted library holds \string— small-press and
        self-published works, chiefly British. Six catalogues have now
        been tried against them. For those, the fields must be filled
        by hand; no further update will change that.
  \item \textbf{\#459 \string— getting back in after losing the
        administrator password.} Until now, an administrator locked
        out of their own installation had to open a database console
        \string— an intimidating detour on a home NAS, for a situation
        that is merely annoying. A single variable,
        \texttt{MYBIBLI\_RESET\_ADMIN}, set in the
        \texttt{docker-compose} file, resets one account at the next
        restart. It works once: leaving the variable in place does not
        re-arm it, and it therefore cannot become a permanent open
        door. The \emph{Operations \& debugging} chapter gives the exact syntax.
  \item \textbf{\#457 \string— a shelf-location code that is actually
        free.} When creating a location, mybibli proposes the next
        available code. It was overlooking deleted locations, which
        keep their code until the definitive purge \string— so the
        proposed code was sometimes already taken and saving failed on
        an error that explained nothing. The proposal now counts them
        and offers the lowest genuinely free code.
  \item \textbf{\#458 \string— a more trustworthy test suite.} Four
        automated tests failed at random, without any actual defect.
        Nothing changes in the application; the point is that a
        failure now means something, instead of prompting a re-run.
\end{itemize}

\section{What's new in 1.15.0}\label{sec:whats-new-1.15.0}

Version 1.15.0 is a minor release on 1.14.1, drawn from a review of a
month of production logs. \emph{One automatic, additive migration; no
operator action.} The new column is nullable and unread by the previous
binary, so rolling back to 1.14.1 stays clean.

\begin{itemize}
  \item \textbf{\#202 \string— a title now says where its description
        came from.} The catalog consults several libraries in turn and
        keeps the first useful answer, but until now it forgot which
        one had replied. Facing a sparse record you could not tell a
        library that answered briefly from one that never answered at
        all. The title page now names the source. Titles catalogued
        before this release show nothing, which is honest: their
        provenance was never recorded, and inventing one would be
        worse than leaving it blank. The library's name is never
        translated \string— it is a proper noun.
  \item \textbf{\#424 \string— readability of faint text.} Several
        secondary texts \string— the counter beside \emph{Recent
        additions}, the placeholders in the volume table, the controls
        in the locations tree \string— were too pale against their
        background to meet the AA accessibility threshold. They have
        been darkened. The effect is subtle by design: these texts
        must stay discreet, only readable.
  \item \textbf{\#419 \string— fewer titles abandoned during a bulk
        metadata run.} When a provider throttles a burst of requests,
        the run retries the affected titles. A third, longer attempt
        has been added: on the measured run, nine titles were being
        written off for want of it. Only throttled titles wait, so a
        clean run is unaffected. Measurement also settled a plausible
        but wrong idea: spacing the requests further out does not
        help, because the refusals do not follow the request rate.
  \item \textbf{\#449 \string— a shorter commit in the log.} The
        startup line printed the full forty-character commit; it now
        prints the seven characters everyone actually compares.
\end{itemize}

\section{What's new in 1.14.1}\label{sec:whats-new-1.14.1}

Version 1.14.1 is a small patch on the 1.14.0 minor. \emph{No

\begin{itemize}
  \item \textbf{\#447 \string— the application identifies itself in

\section{What's new in 1.14.0}\label{sec:whats-new-1.14.0}

Version 1.14.0 is a feature minor on 1.13.0. It fixes three defects in
the cataloging flow and extends bibliographic enrichment to
English-language books. \emph{No database migration — the upgrade is
an image swap against an unchanged schema, and rolling back to 1.13.0
stays clean.} Routine \texttt{docker compose pull \&\& docker compose
up -d}.

\subsection*{Cataloging fixes}

\begin{itemize}
  \item \textbf{\#440 \string— volume labels attached to the wrong
        title.} When several UPC-identified items (typically CDs) were
        cataloged in a row within one browser session, only the first
        established the scan context correctly. The rest left the
        previous title active, so the label scanned next attached to
        that title, or failed with a misleading message if it had
        since been deleted. Every scan path now goes through one
        shared context activation.
  \item \textbf{\#441 \string— misleading error message.} When the
        active title had been deleted, scanning a label answered
        ``not found'', which pointed at the label when the real
        problem was that no item was active. The message now says so,
        and the stale context is cleared so the next scan starts
        clean.
  \item \textbf{\#442 \string— label locked after deletion.} Deleting
        a volume did not release its V-code: the label could only be
        re-used after an administrator permanently purged it from the
        Trash, and the error named its owner ``\texttt{?}''. The label
        is now directly reusable. The previous copy's details
        (condition, location, purchase price, valuation) are discarded
        — it is a different physical object — and recorded in the
        audit trail. Reuse is refused when the deleted volume carries
        loan history, since it would re-attribute that history to a
        different copy.
\end{itemize}

\subsection*{Bibliographic zones for English-language books}

\begin{itemize}
  \item \textbf{\#439 \string— the Library of Congress complements the
        BnF.} The six UNIMARC-aligned fields introduced in 1.13.0
        stayed empty on English-language books: the BnF does not
        catalog them, and the other sources carry no structured
        bibliographic data. mybibli now also reads \textbf{MARC~21}
        records from the Library of Congress.
  \item \textbf{Field-by-field complementarity.} When the source that
        resolved a title fills only some of the six zones, the other
        library is consulted to complete the ones left empty. A value
        already present is never overwritten.
  \item \textbf{Actual reach.} Only books with ISBN prefixes 9780 and
        9781 are affected. \emph{French titles the BnF could not
        describe will stay empty} — the Library of Congress does not
        hold them either. Bear that in mind when reading the backfill
        figures after upgrading.
  \item \textbf{Renamed button.} The Health-tab action is now
        \emph{Backfill metadata from libraries}, since it no longer
        relies on the BnF alone.
\end{itemize}

\section{What's new in 1.13.0}\label{sec:whats-new-1.13.0}

Version 1.13.0 is a feature minor on 1.12.0 centered on one theme:
aligning the catalog with the \textbf{UNIMARC} bibliographic
standard. \emph{One automatic, additive database migration — no
operator action required.} Routine \texttt{docker compose pull \&\&
docker compose up -d}.

\begin{itemize}
  \item \textbf{\#389 \string— UNIMARC-aligned cataloging fields.}
        Titles now carry six additional bibliographic fields mapped
        to their UNIMARC zones: statement of responsibility
        (200\$f), edition statement (205\$a), collection title and
        number (225\$a/\$v), general note (300\$a) and original
        title (500\$a). They are captured automatically from the
        BnF when a book is scanned, and shown on the title page
        whenever present. The authoritative field-to-zone mapping
        ships in the repository as
        \texttt{docs/unimarc-mapping.md}; record import/export
        (ISO~2709 / UNIMARC XML) is a separate, later work package.
  \item \textbf{New Health-tab action: \emph{Backfill metadata from
        BnF}.} Re-runs the metadata lookup for every already-cataloged
        title that has a lookup code, filling the new UNIMARC fields
        (and anything else the providers have learned since) without
        ever overwriting a value you edited by hand. Shares the
        pacing, throttle back-off and single-run lock of the cover
        refetch action.
  \item \textbf{\#434 \string— cataloging log summary.} Every
        metadata resolution now logs a single \texttt{info} summary
        line (cover found? how many UNIMARC fields filled?), which
        makes a backfill run easy to audit from the log file.
\end{itemize}

Version 1.11.0 bundles the four issues raised by the July production-log
review — two bug fixes and two operator-facing improvements. \emph{One

\begin{itemize}
  \item \textbf{\#418 \string— sessions survive a tablet screen-lock.}
        The session cookie is now persistent (its lifetime follows the
        inactivity timeout) instead of a browser-session cookie, so
        iPads and other devices that discard session cookies on lock no

        back-to-back run tripped Google Books' burst throttling and
        silently recovered nothing.
  \item \textbf{\#416 \string— daily auto-purge unblocked.} Leftover
        session rows referencing a long-deactivated user no longer
        block the 30-day hard-purge of that user (a daily error in the
        logs since June). The purge now cleans those rows itself.
  \item \textbf{\#417 \string— quieter logs.} Clicking the dashboard
        \emph{Gaps} chips no longer emits a spurious warning line per
        click.
\end{itemize}

\section{Rollback}

Rollback is \emph{not} a first-class flow. Schema migrations move
forward only — there is no \texttt{down.sql}. The supported recovery
strategy is:

\begin{enumerate}
  \item Restore the pre-upgrade database backup
        (chapter~\ref{ch:backup}).
  \item Pin the image tag back to the prior version.
  \item Start the stack.
\end{enumerate}

This works because the backup is consistent with the prior schema.
Trying to point an older image at a newly-migrated database will
fail to boot.
